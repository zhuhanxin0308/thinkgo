# 性能基准

本页只记录当前源码中可复现的基准入口。历史硬件结果不作为框架契约；比较优化前后数据时必须保持 Go 版本、操作系统、CPU、电源策略、依赖服务和命令参数一致。

## 框架热路径

```powershell
Push-Location framework
try {
    $env:GOWORK = "off"
    go test ./middleware -run '^$' -bench '^BenchmarkPipelineExecution$' -benchmem -count=3
    go test ./route -run '^$' -bench 'Benchmark(RouteMatch|StaticPrefixMatch)$' -benchmem -count=3
    go test ./context -run '^$' -bench '^BenchmarkTrustedProxySetRequest$' -benchmem -count=3
    go test ./http -run '^TestHTTPHealthAllocationBudgets$' -count=1
    go test ./http -run '^$' -bench 'Benchmark(NativeHTTP|SingleAppHTTP|MultiAppHTTP)$' -benchmem -count=3
    go test ./db -run '^$' -bench 'Benchmark(ScanRowsSQLite|ColumnSQLite|StructToMap|GetterPipeline|RelationIndex|ChunkPaginationSQLite|SeekPageSQLite|ConditionChainConstruction|OrderedCursorCompare)$' -benchmem -count=3
} finally {
    Pop-Location
}
```

`ns/op` 是单次迭代耗时，`B/op` 和 `allocs/op` 是每次迭代的分配。HTTP 门禁分别测量原生处理器、单应用兼容形态和两个应用分发，并由 `TestHTTPHealthAllocationBudgets` 约束分配回归。发布工作流会先校验测试及基准符号真实存在，避免正则零匹配形成假绿。路由、管线或请求优化必须同时通过语义测试和 Race Detector，不能只降低某个微基准数字。

## SQLite 完整业务闭环

`tests/business_integration_test.go` 使用临时 SQLite 数据库，经过单应用兼容形态的 HTTP、路由、控制器、中间件、验证器、Session、缓存和 ORM：

```powershell
$env:CGO_ENABLED = "1"
$env:GOWORK = "off"
go test -run '^TestFullBusinessSQLiteIntegration$' -count=1 ./tests
go test -run '^TestFullBusinessSQLiteAllocationBudget$' -count=1 ./tests
go test -run '^$' -bench '^BenchmarkFullBusinessSQLite$' -benchmem -benchtime=2s -count=3 ./tests
```

缓存命中和未命中是不同子场景；未命中场景必须在计时内执行真实 SQLite 查询。该基准证明本地完整调用链，不代表 MySQL、Redis、真实网络或生产容量。

## 外部依赖基准

真实 Redis、MySQL、MongoDB 和 Neo4j 基准位于各自带 `live` 或数据库构建条件的测试文件。运行前必须显式提供测试实例，并使用独立数据库或命名空间；测试结束后只清理本次创建的数据。

`cmd/benchmark` 的 `load` 模式面向已启动的服务，并使用 HDR Histogram 聚合延迟：

```powershell
go test ./cmd/benchmark -count=1
go run ./cmd/benchmark -mode load -base-url http://127.0.0.1:18081 -duration 30s -concurrency 32 -scenario mixed
```

负载结果必须连同错误率、P50/P95/P99、服务端配置、数据库连接池和依赖服务状态一起解释。单机本地结果不能外推为生产容量承诺。
