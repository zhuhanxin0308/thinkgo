# 性能基准

本页只记录可复现的基准入口、场景和指标解释。基准不等同于生产容量承诺，比较时必须保持同一操作系统、Go 版本、CPU、电源策略和命令参数。

## HTTP 分层基准

框架 HTTP 包提供三条同一响应路径：原生 `net/http`、单应用 `Http` 和多应用 `MultiHttp`。三者使用相同的 `ok` 响应、健康请求/小 JSON Body 场景和 `httptest.ResponseRecorder`；计时前会预热路由，单应用和多应用夹具跳过数据库初始化，不访问外部网络、不休眠，也关闭访问日志 I/O。无 Body 场景复用请求对象；JSON Body 场景每次创建新的一次性流，避免把重复消费误测成缓存命中。

运行：

```powershell
go test -mod=readonly ./framework/http -run '^$' -bench '^Benchmark(NativeHTTP|SingleAppHTTP|MultiAppHTTP)$' -benchmem -benchtime=200ms -count=10
```

`ns/op` 或 `µs/op` 是每次请求的平均耗时，`B/op` 和 `allocs/op` 是每次迭代中 recorder、请求处理和响应生成的分配；它们包含基准本身的 recorder 成本，不代表真实网络 socket 成本。当前工作站（Windows amd64、AMD Ryzen 5 7500F）按同一命令运行 10 次、取中位数的实测为：

健康请求的分配预算已作为普通单测门禁：单应用不超过 32 allocs/op，多应用不超过 48 allocs/op。CI 同时运行一次短基准记录 `ns/op`、`B/op` 和 `allocs/op`；时间结果只用于趋势观察，不能替代同硬件的完整压测。

| 场景 | NativeHTTP | SingleAppHTTP | MultiAppHTTP |
|---|---:|---:|---:|
| Health time/op | 295 ns | 2.95 µs | 4.14 µs |
| Health B/op | 274 B | 1840 B | 2680 B |
| Health allocs/op | 6 | 30 | 44 |
| JSONBody time/op | 3.08 µs | 11.37 µs | 11.24 µs |
| JSONBody B/op | 6956 B | 8894 B | 10623 B |
| JSONBody allocs/op | 31 | 60 | 78 |

多应用结果包含应用路径解析、请求克隆和目标应用上下文构造；不应把它与只执行 handler 的原生结果直接当作业务吞吐换算。性能改动必须同时通过路由语义对照、竞态测试和 `allocs/op` 对比。

## 2026-07-29 非数据库性能复测

本轮针对请求生命周期、路由冻结、请求解析、语言检测、JSON 响应、内存缓存、容器和控制器分发完成优化。以下结果来自同一台 Windows amd64 / AMD Ryzen 5 7500F，命令执行 3 次；数值用于比较趋势，不代表生产容量承诺。

```powershell
go test -count=3 -mod=readonly -run '^$' -bench 'Benchmark(NativeHTTP|SingleAppHTTP|MultiAppHTTP)$' -benchmem ./framework/http
```

| 场景 | time/op 范围 | B/op | allocs/op |
|---|---:|---:|---:|
| NativeHTTP / Health | 318–325 ns | 274 B | 6 |
| SingleAppHTTP / Health | 3.06–3.34 µs | 1664 B | 29 |
| MultiAppHTTP / Health | 3.51–3.58 µs | 2432 B | 35 |
| NativeHTTP / JSONBody | 2.89–3.91 µs | 6956 B | 31 |
| SingleAppHTTP / JSONBody | 11.69–12.36 µs | 9438 B | 67 |
| MultiAppHTTP / JSONBody | 10.76–12.08 µs | 10599 B | 75 |

健康请求的单应用分配从历史基线约 41 降至 29，多应用从约 45 降至 35；JSON 响应也减少了不必要的时间值递归复制。多应用仍包含应用解析、请求克隆和上下文构造成本，不能与原生 `net/http` 直接等价比较。

真实 Redis 往返基准使用独立随机命名空间，并在测试结束后清理；本机到已配置 Redis 服务的 3 次结果为：单键顺序 Set+Get 3.08–3.42 ms/次，并发 Set+Get 0.47–0.52 ms/次；32 键批量 SetMany+GetMany 9.53–9.69 ms/次，而 32 键逐键操作为 106.50–108.26 ms/次。该结果验证批量接口显著减少网络往返，但不替代生产网络、连接池和服务端容量压测。

## 延迟负载命令

`cmd/benchmark` 的 `load` 模式面向已启动的 HTTP 服务，延迟由每个 worker 的 HDR Histogram 聚合，再在主 goroutine 合并；不会保存随请求数线性增长的 `[]time.Duration`。输出字段和单位保持兼容：`p50_ms`、`p95_ms`、`p99_ms`、`max_ms` 等仍为毫秒。非负延迟即使低于直方图精度边界也会记录；超过最高可跟踪值、负值或合并丢样本会让本次基准失败并返回错误。

```powershell
go test -mod=readonly ./cmd/benchmark -count=1
go run ./cmd/benchmark -mode load -base-url http://127.0.0.1:18081 -duration 30s -concurrency 32 -scenario mixed
```

`load` 模式需要用户自行启动与场景匹配的服务和数据库；它不是无数据库启动契约的验证入口。无数据库启动和 HTTP 分层基准应使用框架测试夹具或应用自己的无数据库配置完成。

## MySQL 往返优化对照

`cmd/benchmark` 对回环地址保留 `tls=skip-verify` 的本地自签名证书兼容行为；非回环数据库默认使用 `tls=true` 进行证书校验。可通过 `DB_TLS_MODE` 显式选择 MySQL 驱动支持的 TLS 配置名称，生产环境应配置受信任 CA，禁止把 `skip-verify` 当作默认远程策略。对可信的本地 `utf8mb4` 基准库，可以显式设置 `DB_INTERPOLATE_PARAMS=true`，让 MySQL 驱动在客户端合并参数，减少每次查询的 prepare/execute 往返；生产环境不要未经安全评估直接启用。该选项只影响基准进程，默认值为 `false`。

```powershell
$env:DB_INTERPOLATE_PARAMS = "true"
$env:DB_MAX_OPEN_CONNS = "512"
$env:DB_MAX_IDLE_CONNS = "128"
go run ./cmd/benchmark -mode serve -addr 127.0.0.1:18081 -access-log=false
```

连接池上限应按并发和数据库容量实测，不应盲目设置为无限或远高于业务并发；在本地 128 并发基准中，512/128 比 256/64 更稳定，后者会因连接池争用出现失败请求。调整后必须同时检查请求尾延迟、`Threads_running`、提交耗时和失败率。

## 全特性真实业务基准

`full-serve` 使用框架的 `ApplicationManager`、`MultiHttp`、控制器分发和默认中间件流水线。`/bench/full/business` 同一条请求会依次经过 Recovery、语言包解析、Session、全局中间件、控制器中间件、控制器反射调用、验证器、缓存 `Remember`、缓存未命中时的 ORM 查询以及标准 JSON 响应；`/bench/full/cache` 额外覆盖缓存标签写入。基准客户端为每个 worker 保留 Cookie，避免把无状态请求误当成真实 Session 业务。

```powershell
$env:DB_PASS = "root"
$env:DB_NAME = "thinkgo_benchmark"
$env:DB_INTERPOLATE_PARAMS = "true"
$env:BENCHMARK_CACHE_DRIVER = "memory"
$env:BENCHMARK_SESSION_DRIVER = "memory"
go run ./cmd/benchmark -mode full-serve -addr 127.0.0.1:18082 -access-log=false
go run ./cmd/benchmark -mode load -base-url http://127.0.0.1:18082 -duration 20s -concurrency 128 -scenario full
```

本次本地 MySQL 8.0.30、50,000 客户、100,000 商品、100,000 订单和 300,000 订单项的真实链路结果如下。结果包含 HTTP、控制器、中间件、语言、验证、缓存和 ORM，不代表无数据库启动场景。

| Session 驱动 | 场景 | 并发 | RPS | P99(ms) | 失败 |
| --- | --- | ---: | ---: | ---: | ---: |
| memory | full（混合业务） | 128 | 30,346 | 15.29 | 0 |
| memory | full-business（固定商品，稳定 Session） | 128 | 29,823 | 16.81 | 0 |
| file | full-business（固定商品，稳定 Session，默认 TTL） | 128 | 169 | 2,043.67 | 0 |
| file | full（随机商品，需持久化变更） | 128 | 234 | 1,681.92 | 0 |
| file | full-cache-miss（缓存未命中） | 128 | 54,525 | 8.14 | 0 |
| file | full-invalid（验证失败短路） | 128 | 40,577 | 13.54 | 0 |

剖析期间同时生成 `-cpu-profile`、`-heap-profile`、`-mutex-profile` 和 `-block-profile` 四类文件。真实混合请求的 CPU 累计热点为 `MultiHttp.ServeHTTP` 38.45%、`Session.Handle` 30.19%、控制器业务 17.34%、`Cache.Remember` 10.07%、ORM `Query.Find` 8.42%、`Controller.Validate` 3.78%；Windows 高并发下运行时调度和 socket 系统调用占用的采样更多，不能简单归因给 ORM。数据库查询未显示锁等待或临时表落盘问题。

本轮修复了 Session 的幂等写入：在 `session.expire=0` 时，相同 JSON 值重复 `Set` 不再制造版本变更和持久化写入；带 TTL 的 Session 仍保持原有过期刷新语义。文件 Session 的跨进程文件锁是原有驱动实现，本轮没有新增分布式锁；高并发生产环境应按一致性需求选择已有的内存或外部 Session 驱动，而不是把文件驱动当作共享高吞吐存储。
> 兼容说明：幂等写入快路径仅适用于 `session.expire=0`；默认带 TTL 的 Session 仍会在重复 `Set` 时刷新服务端过期时间，保持原有行为。
## 本地 SQLite 完整业务闭环

仓库根目录的 `business_integration_test.go` 会在临时项目中真实启动 `ApplicationManager` 和 `MultiHttp`，使用本地 SQLite 文件建表并植入商品数据；请求链路覆盖控制器反射分发、应用级/控制器级中间件、JSON 请求解析、验证器、多语言、内存缓存 `Remember` 与标签、内存 Session、ORM 查询、健康检查和 HTTP 指标。该测试不需要 MySQL、Redis 或网络服务，CGO 不可用时会明确跳过 SQLite 集成场景。

```powershell
$env:CGO_ENABLED = "1"
go test -mod=readonly -run '^TestFullBusinessSQLiteIntegration$' -count=1 .
go test -mod=readonly -run '^TestFullBusinessSQLiteAllocationBudget$' -count=1 .
go test -mod=readonly -run '^$' -bench '^BenchmarkFullBusinessSQLite$' -benchmem -benchtime=2s -count=3 .
```

2026-07-20 在 Windows amd64、AMD Ryzen 5 7500F 上，启用共享验证计划、控制器便捷验证器缓存、动态控制器中间件直执行和单中间件快路径后的 `2s × 3` 结果中位数约为 38.1 µs/op、23.6 KB/op、282 allocs/op，三轮耗时范围为 35.1–41.2 µs/op；耗时受 Windows 调度和 SQLite 文件 I/O 波动影响，不能把本地基准延迟当作生产容量承诺。相较前一基线，分配量从约 285 降至 282 allocs/op。CI 使用 360 allocs/op 的门禁（留出约 25% 回归余量），基准显式关闭 info 访问日志，生产环境应按日志采集策略另行压测。

在增加有界并行数据库初始化后，同一工作站按相同 `2s × 3` 命令复测为 34.2–44.7 µs/op，中位数约 41.6 µs/op、23.6 KB/op、282 allocs/op。该改动只发生在启动连接建立阶段，不进入请求热路径；本次结果与既有范围重叠，不能据此宣称请求延迟有显著变化。

同一轮 CPU 剖析显示验证规则计划编译已从热路径移除，动态控制器中间件不再创建临时 `Pipeline`，路由中间件也复用注册期管道；当前主要热点为控制器反射调用、Session 解码/初始化、JSON 请求/响应解析和运行时调度，基准中的 SQLite 查询未成为主导瓶颈。共享验证缓存是有界的，仅适用于无场景、无自定义消息的控制器便捷验证，完整 `Validator` 配置 API 的兼容语义保持不变。任何框架级优化都必须重新运行上述闭环、Race 和全量测试，不能用单模块基准替代真实业务验证。
