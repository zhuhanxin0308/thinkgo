# 性能基准

本页只记录当前源码中可复现的基准入口。以下框架测试命令从仓库根目录执行。历史硬件结果不作为框架契约；比较优化前后数据时必须保持 Go 版本、操作系统、CPU、电源策略、依赖服务和命令参数一致。

## 框架热路径

```powershell
$env:GOWORK = "off"
go test ./middleware -run '^$' -bench '^BenchmarkPipelineExecution$' -benchmem -count=3
go test ./route -run '^$' -bench 'Benchmark(RouteMatch|StaticPrefixMatch)$' -benchmem -count=3
go test ./context -run '^$' -bench '^BenchmarkTrustedProxySetRequest$' -benchmem -count=3
go test ./http -run '^TestHTTPHealthAllocationBudgets$' -count=1
go test ./http -run '^$' -bench 'Benchmark(NativeHTTP|SingleAppHTTP|MultiAppHTTP)$' -benchmem -count=3
go test ./db -run '^$' -bench 'Benchmark(ScanRowsSQLite|ColumnSQLite|StructToMap|GetterPipeline|RelationIndex|ChunkPaginationSQLite|SeekPageSQLite|ConditionChainConstruction|OrderedCursorCompare)$' -benchmem -count=3
```

`ns/op` 是单次迭代耗时，`B/op` 和 `allocs/op` 是每次迭代的分配。HTTP 门禁分别测量原生处理器、单应用兼容形态和两个应用分发，并由 `TestHTTPHealthAllocationBudgets` 约束分配回归。发布工作流会先校验测试及基准符号真实存在，避免正则零匹配形成假绿。路由、管线或请求优化必须同时通过语义测试和 Race Detector，不能只降低某个微基准数字。

## SQLite 完整业务闭环

`tests/business_integration_test.go` 使用临时 SQLite 数据库，经过单应用兼容形态的 HTTP、路由、控制器、中间件、验证器、Session、缓存和 ORM：

```powershell
$env:CGO_ENABLED = "1"
$env:GOWORK = "off"
go test -run '^TestFullBusinessSQLiteIntegration$' -count=1 ./tests
go test -run '^TestFullBusinessSQLiteAllocationBudget$' -count=1 ./tests
go test -run '^$' -bench '^BenchmarkFullBusinessSQLite$' -benchmem -benchtime=2s -count=3 ./tests
```

缓存命中和未命中是不同子场景；未命中场景必须在计时内执行真实 SQLite 查询。该基准证明本地完整调用链，不代表 MySQL、Redis、真实网络或生产容量。

## 外部依赖基准

真实 Redis、MySQL、MongoDB 和 Neo4j 基准位于各自带 `live` 或数据库构建条件的测试文件。运行前必须显式提供测试实例，并使用独立数据库或命名空间；测试结束后只清理本次创建的数据。

## 通用业务跨框架比较

独立实验位于 [`benchmarks/business`](../../benchmarks/business/)，比较 ThinkGo、ThinkPHP、Laravel、Gin、Echo、Fiber、Beego 和 Iris。Laravel 分别采用 PHP-FPM 与 Octane / RoadRunner，因此共有九种运行配置。商品目录、商品详情、事务下单、工单评论和混合请求均通过真实 HTTP、PostgreSQL 与 Redis 执行。

[2026-11-07 实测报告](../benchmarks/2026-11-07/REPORT.md) 包含固定版本、业务合同、数据库设计、运行条件、指标定义及完整复现步骤。各实现使用共同 SQL 与数据合同，不把框架 ORM 差异混入这组实验；框架请求生命周期、语言运行时和驱动成本仍然包含在结果中。

先按报告安装锁定依赖并构建独立模块中的应用和负载二进制，再从仓库根目录运行。以下示例使用独立结果目录，不能覆盖已有正式证据：

```bash
python3 benchmarks/business/tools/run.py \
  --runtime ../benchmark-runtime-repro \
  --work ../benchmark-runtime-repro/work/business \
  --output ../benchmark-results-repro/raw \
  --mode measure

python3 benchmarks/business/tools/render.py \
  --input ../benchmark-results-repro/raw \
  --output ../benchmark-results-repro/charts
```

`measure` 先执行统一 HTTP 验收，再运行 `9 配置 × 5 场景 × 2 负载模型 × 3 次重复` 的完整矩阵。闭环固定 64 并发；开放模型在每个业务中对全部配置使用同一个绝对到达率。各轮重新建立业务数据库、固定预热并审计库存、订单金额、明细、评论与版本。

实际负载入口是嵌套模块中的 [`benchmarks/business/go/cmd/load`](../../benchmarks/business/go/cmd/load/)，统一编排入口是 `tools/run.py`。应优先使用编排器完成重置、预热、资源采样和证据校验；单独调用负载程序不会自动完成这些步骤。`verify` 只做功能验收，`pilot` 只做较短的链路检查，不能代替正式性能测量。

图表同时呈现有效吞吐、共同开放负载下的尾延迟、错误、应用 CPU、进程树内存与缓存命中；三轮以中位数和实际最小—最大范围汇总。负载结果必须连同服务配置、数据库连接池、依赖服务及采样完整性解释，单机本地结果不能外推为生产容量承诺。
