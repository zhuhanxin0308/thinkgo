# ThinkGo 开发规范

本规范是 ThinkGo 框架与基于它开发的业务代码的**强制约束**。README 偏重「怎么用」，本文档偏重「必须怎么做、不能怎么做」。两者冲突时以本文档为准。

适用范围：ThinkGo 仓库根目录的框架核心，以及独立业务工程的 `app/<应用名>/`、`config/`、`cmd/` 和测试代码。

---

## 1. 总则

1. **正确性优先于便利**。不允许通过放宽类型检查、跳过错误处理、降低测试质量来「让它先跑起来」。
2. **请求级状态绝不写入全局**。框架是长期运行的多协程进程，任何包级变量、单例字段都可能被并发读写。
3. **默认值兼容**。ThinkPHP 已定义的默认值必须保持一致；项目需要更严格策略时显式覆盖。新增的 Go 扩展能力应采用安全默认（例如删除/更新必须带业务 WHERE）。
4. **复用框架既有能力**：容器、配置、日志、事件、缓存、中间件、验证器。不要另起炉灶。
5. **改动可解释、可测试、可回滚**。每个非平凡改动都要有对应测试，且能说清为什么这么改。
6. 提交前必须在业务工程和框架仓库各自的根目录以 `GOWORK=off` 通过 `go build ./...`、`go vet ./...`、`go test ./...`，禁止只依赖 `go.work` 联合依赖图验证。

## 2. 目录与分层

以下为业务工程的布局；框架通过模块依赖引用，不放入工程内的子目录：

```
app/          项目级定义与 app/<应用名> 业务目录
config/       JSON 配置，文件名即一级命名空间
cmd/          命令行入口
go.mod        依赖 github.com/zhuhanxin0308/thinkgo/v3
public/       静态资源
runtime/      按应用隔离的运行时产物，不入库
docs/         文档
```

- 业务逻辑只能放在 `app/<应用名>` 的对应分层目录；根 `app` 只放项目级服务、事件、中间件、Provider 和生成清单。`main.go` 只组合一个项目 App 与一个原生多应用 HTTP 内核。
- 根清单和每个应用的 `autoload_generated.go` 由 `service:discover` 维护；业务代码不得手工维护注册表，也不得使用包级 `init()` 或全局当前应用完成装配。
- 控制器、模型、验证器、应用路由或应用目录变化后运行 `go run ./cmd/think service:discover`；Air 构建前自动刷新，CI 做只读一致性校验。
- HTTP 请求先按项目规则解析到一个编译期应用。应用身份、公开前缀和重写路径只保存在请求上下文，禁止写入共享 App 字段。
- 框架核心改动需谨慎，必须配套测试，且不得引入对具体业务的依赖。
- 分层依赖方向单向：`main/cmd -> app -> github.com/zhuhanxin0308/thinkgo/v3`。框架核心禁止导入宿主 module 或具体业务包；内部使用接口解耦，避免循环依赖。
- HTTP 业务调用链固定为 `Controller -> Validator -> Service -> Model/ORM`：控制器必须先使用验证器校验参数，只调用服务；服务层优先使用模型和 ORM，复杂查询才使用参数化原生 SQL。
- 业务模型平铺在 `app/<应用名>/model`，不在 `model` 下再创建业务子目录；模型文件按表名命名，不添加模型后缀。

## 3. 命名规范

- 文件名：控制器、路由、中间件、验证器、模型一律小写蛇形（`user_profile.go`）。
- 导出标识符 `PascalCase`，非导出 `camelCase`。
- 控制器导出结构体名必须与路由中的控制器名一致（`type User struct{}` ↔ `"user/index"`）；生成器会自动维护发现入口。
- 数据库表/字段名用小写蛇形；结构体字段用 `thinkgo:"col_name"` 标签映射。
- 常量集中定义，避免散落的魔法值（参考框架根 `constants.go`、各包 `constants.go`）。

## 4. 注释与文档

- **代码注释统一使用中文**，解释「为什么」而非复述「做了什么」。
- 每个导出类型、函数、方法必须有文档注释，首词为标识符本身。
- 对应 ThinkPHP 的能力，注释中标注对应关系，便于迁移者理解。
- 安全相关、并发相关的非显然决策必须写明意图（例如「在写锁内二次检查缓存，保证单例只构建一次」）。
- 新增/调整公共能力时，同步更新 [README.md](../../README.md) 与本规范。

## 5. 错误处理

1. **禁止吞错**。返回 `error` 的调用必须处理：要么向上返回，要么记录日志，要么有明确注释说明为何可忽略。
2. 数据库、文件、网络等 IO 的写操作必须显式处理错误。
3. 行集迭代必须检查 `rows.Err()`，不能因迭代中断而静默返回不完整结果。
   ```go
   for rows.Next() { /* ... */ }
   if err := rows.Err(); err != nil { return nil, err }
   ```
4. 不要对外暴露内部错误细节。生产环境（非 debug）只返回通用信息；详细堆栈与上下文写入日志。异常堆栈页仅在 `debug && 回环地址` 下暴露。
5. 业务错误返回结构化响应（`code`/`msg`/`data`），用 `BusinessException`/`Controller.Error` 等统一出口。
6. `panic` 只用于不可恢复的编程错误；请求处理链中的 panic 由 Recovery 中间件统一兜底，不要依赖 panic 做正常流程控制。
7. `exception.Handle.Render(writer, request, recovered)` 和 `Response.Send(writer)` 都返回 `error`，直接调用时必须处理。HTTP/业务异常状态码只能使用 4xx/5xx；生产环境的 5xx 消息与数据会被统一隐藏。

## 6. 并发与状态

框架是常驻多协程进程，这一节是**事故高发区**，必须严格遵守。

1. **请求级对象不得跨请求共享**：`*context.Request`、`*context.Response`、控制器实例、请求级 Session/Cookie 都是每请求新建。控制器通过容器工厂模式（`BindFactory`）每次请求 `reflect.New` 出新实例；需要在一次请求内复用并自动释放的业务服务使用 `BindScoped`，通过 `Request.Make` 解析。
2. **不要把请求数据写入包级变量或单例字段**。需要跨中间件传递时用 `req.Set()` / `req.GetData()`（内部有读写锁保护）。
3. **共享可变状态必须加锁**，并保证锁粒度与顺序一致：
   - 并发解析同名单例必须共享一次构建；循环依赖必须返回错误。重绑定、显式实例覆盖或删除服务后，旧的在途构建不得重新写回容器。
   - map 的并发读写必须用 `sync.RWMutex` 或 `sync.Map` 保护（如缓存 store 注册表、配置查询缓存、验证器正则缓存）。
4. **持锁期间避免回调用户代码或递归解析**，防止死锁。
   - 容器工厂解析依赖时必须使用工厂参数注入的作用域容器，禁止闭包捕获外层容器后递归调用。
5. **map 遍历顺序不确定**：依赖顺序的场景（如校验错误「第一条」、批量字段顺序）必须显式排序。
6. 后台协程（会话回收等）必须提供可停止的退出机制，并在进程退出时关闭。

### 6.1 框架启动与生命周期

- `config/database.json` 缺失表示数据库未启用；框架必须仍能初始化路由、缓存、模板、日志和 HTTP，并允许非数据库请求正常工作。只有显式存在且格式错误的数据库配置才形成启动错误。
- 项目入口在监听前构建并初始化全部编译期应用、Boot Service 并冻结全部路由；任一应用失败必须整体阻断。单个请求仍由目标应用的 `Http.Run`、`Http.End` 处理，项目 `App.Close` 逆序关闭所有子应用。
- 框架核心不依赖数据库、Redis、租约或任何分布式锁来保证单进程启动和请求处理。需要跨进程一致性的业务能力必须由业务层明确选择后端，并单独记录失败语义。
- HTTP 内核通过 `app/request.go` 为每个请求创建独立 Request；请求体只消费一次，并由 Request 负责大小限制、缓存和关闭，测试必须覆盖未知长度流和并发隔离。

## 7. 安全规范

### 7.1 SQL 与标识符

- **值一律参数化**（`?` 占位符），由方言层 `Rebind` 转换；**绝不**把用户输入拼进 SQL 字面量。
- **标识符（表名、字段名、操作符、排序）一律走白名单校验**：`validateIdentifier`、`validateIdentifierList`、`validateOrderClause`、`normalizeOperator`、`validateJoinCondition`。新增任何拼接标识符的入口，都必须先过这些校验。
- 优先使用参数化 API：`WhereField` / `WhereMap` / `WhereIn` / `WhereBetween` / `WhereLike` / `WhereNull`。
- `WhereRaw` / `HavingRaw` / `DB.Query` / `DB.Execute` 是**显式逃生舱**，不做标识符校验，调用方必须自行保证参数化与输入安全，且应在代码评审中重点审查。
- `Update` / `Delete` / `ForceDelete` 禁止无 WHERE 执行（框架已强制），不要绕过。

### 7.2 路径穿越

- 任何把外部输入拼成文件路径的地方（视图模板名、下载文件、静态资源），必须做 `..`/绝对路径净化并校验真实路径落在允许的根目录内（参考 HTTP 内核 `openPublicFile`、视图驱动 `safeTemplatePath`、`Response` 的 `resolveWithinBase`）。
- `Response.Download(path, filename)` 的 `path` 必须是受信任路径；`filename` 已由框架净化（取末段、去引号与换行）以防 `Content-Disposition` 头注入。
- **下载路径可能来自用户输入时，必须使用 `Response.DownloadSafe(baseDir, relativePath, filename)`**：它会拒绝绝对路径与 `..` 逃逸，确保最终文件落在 `baseDir` 内，越界返回 403。禁止把未校验的用户输入直接传给 `Download`。

### 7.3 输出与注入

- HTML 输出统一用 `html/template`（自动转义）；调试条等服务端拼接 HTML 必须对所有动态片段 `html.EscapeString`。
- JSONP 回调名必须白名单校验后才输出（框架已实现，不要绕过）。
- 重定向 `Location` 不要直接回显未校验的用户输入，防开放重定向。
- 响应头名或值包含控制字符时会被整体拒绝；`Connection`、`Content-Length`、`Transfer-Encoding` 等逐跳或分帧字段只能由 HTTP 内核管理。

### 7.4 鉴权、代理与会话

- 客户端 IP / 协议只在请求来自**可信代理网段**时才信任 `X-Forwarded-For` / `X-Forwarded-Proto`；可信网段通过 `trusted_proxies` / `SERVER_TRUSTED_PROXIES` 配置，默认空（不信任）。
- 登录、提权等敏感操作后必须检查 `Session.Regenerate()` 的返回错误，退出登录必须检查 `Session.Destroy()`；旧 ID 的撤销墓碑用于阻止并发旧请求复活会话，业务代码不得绕过 Session 驱动直接删文件。
- GET/HEAD 静态文件会经过全局中间件，但在路由匹配前直接响应，不会经过路由、分组或控制器中间件；依赖路由级鉴权的资源不要放在 `public/`。需要修改直接响应头的全局中间件必须在调用下游前写入原生 `ResponseWriter`。
- ThinkPHP 默认 `url_route_must=false`，自动路由开启；不希望被路由的辅助方法不要导出，严格生产项目应显式设置 `url_route_must=true`。

### 7.5 密钥与敏感信息

- 密钥、密码、证书私钥**禁止入库**：`.env`、`runtime/` 已在 `.gitignore` 中，编译产物（`*.exe`、二进制）同样不入库。
- 生产环境禁止系统环境变量 `APP_APP_DEBUG=true` / `APP_APP_TRACE=true`（`.env` 段落写法为 `[APP] APP_DEBUG=true` / `APP_TRACE=true`）；Cookie/Session 在 HTTPS 下应置 `secure=true`。`cookie.secret` 与 `csrf.secret` 使用至少 32 字节的外部密钥，多实例必须保持一致且不得写入版本库。
- 日志/异常页对 `password`、`token`、`authorization`、`cookie` 等敏感字段必须脱敏（框架已实现，扩展时沿用 `isSensitiveKey`）。

## 8. 数据库与 ORM 规范

- 控制器禁止直接调用模型、`db.DB` 或查询构造器；数据库访问由服务/仓储层封装，控制器只处理请求验证、服务调用和响应转换。
- 每次链式查询是独立 `Query` 实例，不跨请求复用状态；需要复用基础条件时用 `clone()`。终端方法（`Find`/`Count`/`Select` 等）在克隆上执行，不污染原查询。
- 写操作处理错误并检查受影响行数。框架会复制写入 map；批量插入要求各行字段集合一致，`InsertAll` 超过占位符上限会自动分批并包裹事务保证原子性。
- 表前缀由配置统一追加：`Name()` 加前缀，`Table()` 用完整表名；JOIN 表跟随主表的前缀规则。JOIN 默认只投影主表列，关联表字段必须显式选择并为同名列设置唯一别名。
- 自动时间戳、软删除、获取器/修改器/搜索器走 Model 层统一能力，不要在业务层手搓；软删除自动条件不能代替更新、删除或恢复所需的业务 WHERE。
- 框架内部和持久化时间统一使用 UTC；业务代码优先使用 `app.Now()`，直接读取系统时间时必须调用 `time.Now().UTC()`。用户所在地区的时间只在输入解析或展示边界显式转换，禁止依赖 `time.Local`。
- 事务优先用 `DB.Transaction(fn)` / `DB.TransactionContext(ctx, fn)` 闭包形式，自动 Commit/Rollback；业务错误与回滚错误会聚合，panic 会回滚并重新抛出。
- HTTP 请求内的查询/事务应通过 `WithContext` / `TransactionContext` 传入请求 context，使慢查询随请求取消，避免拖垮连接池。
- 分页大偏移量（OFFSET）性能差且并发增删会漏/重，海量数据遍历用 `ChunkById`（主键游标）；游标字段必须存在、类型稳定且严格递增。
- `Count`/`Paginate` 对 JOIN/GROUP/DISTINCT 会自动包子查询统计真实 total，无需手写。
- 跨方言：SQL 统一 `?` 占位符由 builder 转换；PostgreSQL 自增主键使用 `INSERT … RETURNING <primary_key>`，非 `id` 主键必须通过模型 `PrimaryKey` 声明。
- 数据库错误日志只记字段名与参数数量，禁止把字段值/绑定参数写入日志；SQL 字符串、dollar quote 与注释内容必须先脱敏。

## 9. 配置规范

- 配置文件 `config/*.json`，文件名即一级命名空间。
- 项目配置放在根 `config/`，单个业务应用的差异放在 `app/<name>/config/`；遗留 `app/config` 不会被读取。环境变量优先于两层文件配置。监听地址、TLS、HTTP/3 和应用解析规则固定使用项目快照，业务应用覆盖层不能改变宿主监听边界。
- 配置字段和默认值必须对照本地 ThinkPHP 项目；Go 宿主扩展字段应保持显式命名、严格校验和安全默认。
- **读取用类型安全访问器** `GetBool` / `GetInt` / `GetString` / `GetMap`，缺失或类型不符时回退默认值；**禁止**对裸 `Get` 的返回值直接做类型断言（`.(bool)`、`.(map[...])`），那会在配置异常时让进程启动即 panic。
- **`Get` / `GetMap` 对 map 和 slice 返回递归隔离的快照**：调用方修改返回值不会污染共享配置；`GetMapCopy` 保留为相同语义的兼容名称。
- **所有配置写入只能经由 `Set`**（持写锁、失效查询缓存）。覆盖嵌套配置用点路径，如 `Set("app.server.tls.enable", true)`，`Set` 会自动创建缺失的中间子树——不要用「`Get` 取出 map → 原地改 → 再 `Set`」的模式去修改共享引用。
- 优先级：`.env`/环境变量 > 应用配置覆盖 > 项目级 `config/*.json` > 框架默认值；应用配置不能越过宿主监听边界。
- 新增配置项必须有合理默认值；安全边界配置的类型、范围或键名非法时必须返回启动错误，禁止截断或静默回退。
- MySQL 默认启用 TLS 并校验证书；仅可在受信任开发环境的 `database.connections.*.params.tls=skip-verify` 中显式跳过校验，生产环境必须保留证书校验；`tls_verify` 不是支持的框架字段。
- `.env` 仅写入框架内部存储，不调用 `os.Setenv`，避免敏感值泄漏到子进程环境。
- `.env` 缺失可忽略；其他 IO、扫描和语法错误必须传播。布尔变量统一使用 `Env.GetBool` 并检查错误，非法值禁止回退默认值。

## 10. 缓存规范

- 所有缓存返回错误必须处理。`Get` 必须同时处理 `found` 与 `error`，禁止用 `value == nil` 判断未命中；命中的 nil 是合法缓存值。
- `Remember` 回调必须返回 `(interface{}, error)`，加载或写入失败必须向上传播。同进程合并加载不能替代跨进程防击穿锁。
- Memory 保留 Go 动态类型，并复制常见可变值；File、Redis、DB 使用 JSON，反序列化后的 JSON 数值为 `float64`，业务读取时必须做受控转换。
- Redis store 默认必须配置非空 `prefix`。空前缀默认拒绝 `Flush()`；只有独占 DB 才可显式设置 `allow_flush_db=true`，此时按 SCAN 清理所选 DB 的缓存键并保留 ThinkGo 活动锁。
- 所有 Redis 操作带超时（`timeout_ms`），避免后端抖动拖垮请求协程。
- `Inc`/`Dec` 只接受精确 `int64` 值和非负步长；Redis 上为后端原子操作，跨进程计数优先使用 Redis。
- 标签写入失败必须保持补偿回滚；Memory、File、Redis 的跨管理器标签元数据变更会先取得 store 级互斥锁，DB 仍只提供当前管理器内的串行语义。
- `Flush` 不得释放 Memory、File 或带前缀 Redis 中的活动锁。文件清理只能删除驱动管理的 `.cache` 与陈旧临时文件，不能删除 `.lock` 或目录内其他文件。
- 直接创建缓存管理器时必须调用并处理 `Close()`；应用资源统一由 `app.Close()` 关闭，禁止在活动缓存调用期间自行关闭驱动。

## 11. 日志规范

- 通过 `app.Log()` 取得日志器后按级别记录；带上下文用 `*Ctx` 方法传 `map[string]interface{}`。
- 不同类别日志用命名通道（`logger.Channel("sql")`）隔离。
- 日志异步批量刷盘；需要确认写入完成时调用 `Flush(ctx)`。绕过 `app.Run()` 时必须调用 `app.Close()` 并处理聚合的应用服务、缓存、数据库和日志关闭错误。
- 不要在热路径打印大对象；敏感字段先脱敏。

## 12. HTTP / 中间件 / 控制器规范

- 中间件签名固定：`func(*context.Request, func(*context.Request) *context.Response) *context.Response`，必须调用 `next(req)` 或显式短路返回。
- 中间件拿到下游响应后要判空再设置头部（下游可能返回 nil）。
- 执行顺序：项目全局 → 应用级 → 路由 → 控制器中间件 → 控制器动作；终结逻辑用 `Lifecycle`/`PipeLifecycle`。
- 控制器每请求新建，禁止字段缓存请求级状态；返回 `string`/`*Response`/任意可 JSON 化对象。
- 控制器内通过 `c.App`、`c.Request` 访问框架能力，不要访问包级单例。
- 应用组件使用 ThinkPHP 多应用定义：控制器放在 `app/<name>/controller`，路由放在 `app/<name>/route`，应用中间件、事件与 Provider 放在同一应用目录；根 `app` 只声明项目级能力。禁止手写注册表或在包初始化阶段维护可变全局状态。
- URL 处理使用 `app.URL`、`app.URLFor`、`app.RouteURL` 或 `app.Route().URL`，不要手工拼接域名和路径。
- 应用服务的 `Register`、`Boot` 以及可选关闭方法必须返回真实错误；生命周期回调中禁止再次 `Initialize`、`Run` 或 `Close` 同一应用。
- 业务路由使用 `*framework.Route` 的 ThinkPHP 风格链式 API，例如 `Route.Get(...).Name(...).Pattern(...)`。分组默认使用与 ThinkPHP 相同的无参回调并继续调用 `Route.Get(...)`；需要显式作用域时也可接收 `*framework.RuleGroup`。
- `http.NewHttp` 返回的配置错误必须在赋值给 `app.Kernel` 前处理；请求体 `Parse` 错误必须在进入业务前转换为 400/413。
- 事件 `Listen`、`Subscribe`、`Dispatch` 的错误必须处理，监听器与订阅者实现也必须返回错误。
- 验证器配置统一使用 `SetRules`、`SetMessages`、`SetScenes`。控制器的 `Validate` 与 ThinkPHP 一样在失败时抛出验证异常；需要显式结果时调用 `ValidateResult`，先处理配置 `error`，再判断 `Result.Valid()`。禁止恢复共享 `Check/GetError` 状态模式。

## 13. 测试规范

- 新功能、修复、重构**先写有意义的测试**，验证行为而非堆覆盖率。
- 修 bug 时先写能复现的失败用例，再修。（本项目的 JOIN 带空格条件 bug 即由新增测试暴露。）
- 涉及文件/缓存/数据库/会话等 IO 的测试必须用临时目录并清理（`t.TempDir()`、`t.Cleanup`）。
- 框架核心测试放对应包，并从框架仓库根目录以 `GOWORK=off` 执行；应用集成测试可放业务项目根，验证注册链路与真实 HTTP 行为。
- 多应用测试必须使用独立临时根目录，覆盖应用选择、配置/容器/路由隔离、监听前失败、并发请求、HTTP 生命周期和逆序关闭；单应用兼容也必须使用同一原生内核验证。框架发布还要证明独立下游宿主可解析并编译公共模块。
- 安全相关能力必须有「拒绝恶意输入」的负向测试（参考 `query_security_test.go`）。
- 提交前宿主与框架两个模块的 `go test ./...` 都必须全绿；并发敏感代码尽量用 `go test -race`（需 CGO）。

## 14. 依赖管理规范

- 业务工程与框架分别维护 Go Modules，不提交 `vendor/`；新增依赖后只在依赖所属模块以 `GOWORK=off` 执行 `go mod tidy`。ThinkGo 仓库只发布根目录的 v3 框架模块。
- 升级：分别在两个模块中使用 `GOWORK=off go get -u ./...` 升到同主版本内最新，再各自执行 `go mod tidy && go build ./... && go test ./...`。
- 跨大版本（`/v2`、`/v3`）升级是破坏性变更，单独评估并改造代码与测试，不在常规升级中顺带。
- 优先选择**维护中**的依赖，避免已废弃/归档库（如 SQL Server 驱动用 `microsoft/go-mssqldb` 而非已废弃的 `denisenkom/go-mssqldb`）。
- 注意 retracted（撤回）版本，及时升级到修复版。
- 依赖抬高 `go` 指令最低版本时，确认团队工具链可用（`GOTOOLCHAIN=auto` 会自动拉取），或权衡后锁定不抬高版本的依赖。
- 提交前分别在两个模块中执行 `GOWORK=off go mod verify` 校验完整性。国内代理：`GOPROXY=https://goproxy.cn,https://goproxy.io`。

## 15. 提交与评审

- 一次提交聚焦一件事，信息说清「做了什么、为什么」。
- **禁止批量脚本式无差别改代码**，改动逐文件进行、可解释。
- 禁止提交编译产物、运行时文件、密钥。
- 评审重点：错误处理是否完整、是否引入共享可变状态、是否有未参数化的 SQL/未校验的标识符、是否绕过安全默认、是否有对应测试。

## 16. 性能注意事项

- 启动期一次性严格解析配置，热路径避免重复类型转换与配置树遍历（参考 HTTP 内核 `parseHTTPConfig`）。
- 路由：注册完成后调用 `Freeze` 构造只读索引；静态路由走 map O(1)，动态路由复用一次解析的路径段，正则在注册期编译。
- 避免对大响应体做整体复制/小写化（Trace 仅对 HTML 响应处理）。
- 文件句柄、连接等资源要复用并在合适时机释放，避免随时间泄漏。
- 数据库连接池参数（最大连接数、生命周期）按部署环境配置，不硬编码。
