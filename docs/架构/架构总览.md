# 架构总览

ThinkGo 的组合根仍是一个项目入口 `framework.App` 和一个 `framework/http.Http`，但入口 App 持有编译期应用目录，HTTP 内核内部原生构建和分发多个独立应用，不存在第二套 `ApplicationManager` 或 `MultiHttp` 运行入口。

```text
main / cmd
    │
    ▼
app.Register -> ApplicationDefinition[]
    │
    ▼
项目入口 App
    ├── 项目配置快照与全局定义
    ├── index App（入口实例复用）
    ├── admin App（独立实例）
    └── ...
    │
    ▼
framework/http.Http
    ├── 项目监听配置
    ├── 只读应用解析器
    └── 每应用 Http 处理器
          ↓
Request -> 全局中间件 -> 应用中间件 -> Route -> Controller -> Response
```

## 两层配置

项目 `config` 先加载并形成不可变快照，用于应用选择、宿主监听和共享默认值。随后每个应用从同一项目快照出发叠加 `app/<name>/config`。应用配置互不克隆，也不能反向改变 `default_app`、映射、域名绑定或监听端口。

## 应用隔离

每个应用拥有独立：

- Container 与请求 `ContainerScope`；
- Config、Provider、Event、Middleware、Route；
- Log、Cache、Session、Lang、View、DB、Migration 和 Telemetry；
- `runtime/<name>` 运行目录；
- 初始化、Boot 与关闭状态。

请求中的应用身份保存在请求上下文，不写入进程级可变“当前应用”。并发访问不同应用不会修改共享 App 元数据。

## 启动与关闭

```text
NewAppUninitialized
  -> 注册项目和应用清单
  -> 加载项目 config 并捕获快照
  -> 初始化所有应用、Boot Provider
  -> 加载并冻结所有应用路由
  -> 构建应用解析器
  -> 校验 TLS/HTTP3 后监听
  -> 请求分发
  -> 项目 App 逆序关闭子应用和受管资源
```

任一编译期应用在配置、Provider、路由或冻结阶段失败，网络监听不会开始。单应用只是清单中只有一个 `index` 的兼容形态，使用相同内核和生命周期。

业务调用链保持 `Controller -> Validator -> Service -> Model/ORM`。入口只组合，不承载业务规则。
