# 架构总览

ThinkGo 采用“应用实例 + 应用管理器 + 统一 HTTP 宿主”的架构。每个应用拥有独立的 `framework.App`、容器、路由、中间件管道、事件分发器、配置和运行时目录；一个进程可以同时加载多个应用，但只启动一个 HTTP/TLS/HTTP3 监听器。

本章只说明对象关系和生命周期。请求选择见[请求流程](请求流程.md)，应用目录和解析规则见[多模块和多应用](多模块和多应用.md)。

## 项目分层

ThinkGo 项目按宿主资源、应用资源和框架实现分层：

```text
.
├── config/                         # 项目级配置和统一监听器配置
├── app/
│   ├── index/                      # 默认应用
│   │   ├── application.go          # 应用定义和组件注册入口
│   │   ├── controller/
│   │   ├── middleware/
│   │   ├── model/
│   │   ├── validate/
│   │   ├── lang/
│   │   └── route/
│   └── admin/                      # 另一个独立应用，结构与 index 对齐
├── framework/                      # 框架实现
├── cmd/think/                      # 多应用 CLI
├── main.go                          # HTTP 宿主入口
└── public/                         # 项目级公共静态资源
```

控制器、中间件、模型、验证器、多语言和路由定义必须放在所属应用目录下。`application.go` 是应用的组合入口，负责把本应用的组件注册到传入的 `*framework.App`；组件包不再通过全局注册表相互共享。

## 核心对象

### `framework.App`

`framework.App` 是单个应用的组合根，持有：

| 能力 | 说明 |
|---|---|
| 容器 | 控制器工厂、Provider、显式实例和服务绑定 |
| 配置与环境 | 项目配置、应用配置和环境变量覆盖 |
| 路由与中间件 | 当前应用的路由快照和请求管道 |
| 事件 | 当前应用独立的生命周期和业务事件分发器 |
| 数据与基础设施 | 数据库、缓存、日志、视图、语言、Cookie、Session |
| 目录边界 | `ApplicationPath`、应用资源目录和应用运行时目录 |

请求级对象由当前应用的 HTTP 处理器创建；请求、响应、控制器实例和应用上下文不能写入包级变量或跨应用共享。

### `framework.ApplicationManager`

`ApplicationManager` 管理同一进程内的应用集合和生命周期：

1. 按编译期 `ApplicationDefinition` 创建每个 `App`。
2. 为每个应用调用自己的 `Register(*App)`，完成控制器、路由加载器、中间件、Provider 和事件注册。
3. 在监听前初始化并启动全部应用；任一应用初始化或 Provider 启动失败，宿主不得监听。
4. 维护默认应用、应用解析器和跨应用 URL 作用域。
5. 退出时按应用注册逆序关闭资源。

### `framework/http.MultiHttp`

`MultiHttp` 为每个应用创建一个内部 `Http` 处理器，但只使用一份服务器配置和一组 HTTP/TLS/HTTP3 监听器。请求先由 `ApplicationResolver` 选择应用，再克隆请求、重写应用路径并交给目标应用处理器。

```text
main.go / cmd/think run
          │
          ▼
ApplicationManager
   ├── App(index) ── application registry / route / middleware / Event
   ├── App(admin) ── application registry / route / middleware / Event
   └── ApplicationResolver
          │
          ▼
       MultiHttp ── one HTTP/TLS/HTTP3 listener
          │
          ├── request -> index Http
          └── request -> admin Http
```

## 应用注册入口

每个应用通过 `application.go` 暴露一个注册函数，并在包初始化阶段只登记应用定义：

```go
package index

import (
	"thinkgo/app/index/controller"
	appmiddleware "thinkgo/app/index/middleware"
	"thinkgo/framework"
)

// Register 注册 index 应用自己的组件。
func Register(app *framework.App) error {
	if app == nil {
		return framework.ErrNilApplication
	}
	if err := app.RegisterController("User", &controller.User{}); err != nil {
		return err
	}
	return app.RegisterGlobalMiddleware(appmiddleware.RequestID)
}

func init() {
	framework.MustRegisterApplication(framework.ApplicationDefinition{
		Name: "index", Path: "app/index", Register: Register,
	})
}
```

`init` 不应把控制器、中间件或路由写入跨应用的包级注册表。旧的包级注册 API 只为单应用兼容流程保留，多应用管理器只消费每个 `ApplicationDefinition` 的注册回调。

## 生命周期

```text
注册 ApplicationDefinition
        │
        ▼
创建所有 App
        │
        ├─ Register(app)：组件注册到当前 App
        ├─ Initialize：配置、资源、路由加载
        └─ 生成 ApplicationResolver / MultiHttp
        │
        ▼
ApplicationManager.Boot
        ├─ 检查所有应用启动错误
        ├─ Provider.Register 已在应用注册阶段完成
        ├─ AppInit
        ├─ Provider.Boot
        └─ RouteLoaded
        │
        ▼
冻结全部应用路由并启动唯一监听器
        │
        ▼
请求解析应用 -> 克隆请求 -> 目标 App.Http 处理
        │
        ▼
监听器退出 -> 应用按逆序 Close
```

`Register` 适合绑定服务、注册控制器、路由加载器和监听器；`Boot` 适合在所有注册完成后检查依赖并启动后台资源。重复启动、关闭和 Provider 注册错误必须返回错误，不能让半初始化应用开始监听。

## 宿主级与应用级资源

| 资源 | 所属范围 | 规则 |
|---|---|---|
| `config/` 中的服务器、TLS、HTTP/3 | 项目/宿主 | 所有应用必须使用一致的监听配置 |
| `public/`、异常模板 | 项目/宿主 | 由统一宿主提供，不随请求应用切换 |
| `app/<name>/config` | 应用 | 在项目配置后加载，只覆盖当前应用配置 |
| `app/<name>/lang`、`view` | 应用 | 由当前 `App` 独立读取 |
| `runtime/<name>/` | 应用 | 日志、缓存、Session 等运行时文件隔离 |
| `controller`、`middleware`、`model`、`validate`、`route` | 应用 | 只能注册到所属 `App` |

应用代码需要跨应用共享时，应提取为不持有当前应用状态的独立框架或内部包；不能把某个应用的容器、路由、事件或请求对象放到共享单例中。

## HTTP 内核边界

目标应用的 `framework/http.Http` 负责请求解析、Host 校验、静态资源处理、应用中间件、路由匹配、控制器分发、异常恢复和请求收尾。它不负责决定请求属于哪个应用，这项工作由统一宿主在克隆请求前完成。

业务调用链保持：

```text
Controller -> Validator -> Service -> Model/ORM
```

控制器负责请求输入和响应转换，服务负责业务编排，模型负责数据映射，框架包负责通用能力和生命周期。
