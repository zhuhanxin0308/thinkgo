# 服务

ThinkGo 中的“服务”有两层含义：

1. `framework.ServiceProvider` 是框架级服务提供者，负责把能力接入应用生命周期。
2. `app/<应用名>/service` 是业务服务与仓储层，负责组合验证后的业务参数、模型/ORM、事务和外部依赖。

两者可以协作，但职责不同。Provider 负责装配，业务服务负责业务规则；控制器不应直接承担数据库查询和事务编排。

## 服务提供者接口

服务提供者实现 `framework.ServiceProvider`：

```go
type DemoService struct {
	logger interface{}
}

func NewDemoService(logger interface{}) *DemoService {
	return &DemoService{logger: logger}
}

type DemoProvider struct{}

func (p *DemoProvider) Register(app *framework.App) error {
	app.Bind("demo.service", func() interface{} {
		return &DemoService{}
	})
	return nil
}

func (p *DemoProvider) Boot(app *framework.App) error {
	// 所有 Provider 完成 Register 后，再启动需要协作的能力。
	return nil
}

func (p *DemoProvider) Shutdown(app *framework.App) error {
	// 释放 Provider 自己持有的连接、协程和外部资源。
	return nil
}
```

`Shutdown` 不是 `ServiceProvider` 必需方法。需要释放资源的 Provider 额外实现 `framework.ServiceProviderShutdown` 即可。

## 注册与启动顺序

通过应用注册 Provider：

```go
if err := app.RegisterProvider(&DemoProvider{}); err != nil {
	return err
}
```

Provider 也必须注册到所属应用的 `application.go`，不能通过一个全局 Provider 列表同时注入所有应用：

```go
if err := app.RegisterProvider(service.NewBilling(app)); err != nil {
	return err
}
```

应用启动时按以下顺序处理：

```text
RegisterProvider
  └─ Provider.Register
       ↓
BootProviders 关闭注册阶段并等待在途 Register
       ↓
AppInit
       ↓
Provider.Boot（按注册顺序）
       ↓
RouteLoaded
       ↓
HTTP 内核运行
       ↓
Provider.Shutdown（按注册逆序）
```

`Register` 只做绑定服务、注册监听器等装配工作，不依赖其它 Provider 已经完成启动。`Boot` 在全部 `Register` 成功后执行，适合检查依赖、建立连接或启动后台任务。

注册阶段关闭后不能再添加 Provider。Provider 必须是非空指针；重复注册、注册失败、启动失败、关闭失败和回调 panic 都会返回错误或进入应用启动/关闭错误聚合。

## Provider 与容器

Provider 通常通过容器绑定服务：

```go
func (p *DemoProvider) Register(app *framework.App) error {
	app.Bind("demo.service", func(container *framework.Container) (interface{}, error) {
		logger, err := container.Make("log")
		if err != nil {
			return nil, err
		}
		return NewDemoService(logger), nil
	})
	return nil
}
```

工厂依赖必须通过注入的容器解析，错误必须向 `Register` 返回。Provider 不应把请求级对象绑定为单例，也不应在 `Boot` 中重新调用同一个应用的 `Initialize`、`Run` 或 `Close`。

## 业务服务层

业务服务放在 `app/<应用名>/service`，典型职责是：

- 接收 `context.Context` 和已明确的业务参数。
- 调用验证后的业务规则、模型和 ORM。
- 组合事务、缓存、日志和外部服务。
- 将底层错误转换为业务层可以处理的错误。
- 不把查询构造器、数据库行集或内部连接细节暴露给控制器。

控制器调用链固定为：

```text
Controller -> Validator -> Service -> Model/ORM
```

控制器只负责请求读取、验证器调用、服务调用和响应转换。服务层优先使用模型/ORM，只有 ORM 无法清晰表达时才使用参数化原生 SQL。

## 关闭责任

`App.Run()` 会在内核退出、启动失败或运行 panic 后调用 `App.Close()`。直接创建应用、缓存、日志或数据库驱动的工具必须自行调用并处理关闭错误；应用正在运行时，外部不能抢先关闭仍被内核使用的共享资源。

Provider 的关闭应保持幂等，后台协程必须有明确的停止机制。需要观察完整启动顺序时阅读[请求流程](请求流程.md)，需要理解依赖绑定时阅读[容器和依赖注入](容器和依赖注入.md)。
