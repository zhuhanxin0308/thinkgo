# 请求流程

ThinkGo 的请求流程分为“统一宿主选择应用”和“目标应用 HTTP 内核处理”两段。这样既能让多个应用共用一个监听器，也能保证每个应用使用自己的路由、中间件、容器、事件和运行时资源。

## 启动阶段

HTTP 监听前，入口执行以下步骤：

1. 包初始化登记所有 `ApplicationDefinition`。
2. `ApplicationManager` 为每个定义创建独立的 `framework.App`。
3. 调用每个应用的 `Register(app)`，注册控制器、路由加载器、全局中间件、Provider 和事件。
4. 每个应用加载项目配置、应用配置、语言包、视图、缓存、日志、Session、可选数据库和路由；缺少 `config/database.json` 不会阻止非数据库模块启动。
5. 创建 `MultiHttp`，为每个应用创建内部 `Http` 处理器，并校验所有应用的宿主配置一致。
6. `MultiHttp.Run()` 把 Provider 启动、路由冻结、宿主监听和应用关闭交给同一个 `ApplicationManager` 生命周期。
7. 只有上述步骤全部成功后，统一 HTTP/TLS/HTTP3 监听器才开始接收请求；任一应用初始化或 Provider 启动失败，宿主不会监听。

`ApplicationManager` 是生命周期唯一所有者。调用方不应在 `MultiHttp.Run` 外部手工交错 `Boot`、`Run` 和 `Close`；关闭会按应用启动的逆序执行。框架不要求数据库或分布式锁才能完成上述非数据库 HTTP 流程。

## 统一宿主选择应用

请求先进入 `framework/http.MultiHttp.ServeHTTP`，不会直接进入某个应用的 `Http`：

1. 校验请求 URL、转义路径和 Host，拒绝编码斜杠、编码点段、反斜杠、控制字符和非法 Host。
2. 优先按 `domain_bind` 选择应用。
3. 没有域名绑定时读取 URL 首段，按应用名称或 `app_map` 别名选择应用。
4. 处理 `deny_app_list`、未知应用和 `app_express` 规则。
5. 生成 `ApplicationResolution`，保留原路径、重写路径、路径前缀和域名绑定标记。
6. 克隆 `http.Request`，只在克隆对象上重写路径和 `RequestURI`，原始请求不被修改；`Body` 保持同一个一次性流，不在 `MultiHttp` 层预读、复制或提前关闭。
7. 创建不可变的 `context.ApplicationContext`，交给目标应用的 `Http` 处理器。

路径应用的前缀会从克隆请求中移除。例如 `/admin/users` 选择 `admin` 后，目标应用看到 `/users`；域名绑定应用不移除路径。原始路径仍可通过请求应用上下文读取。

```text
原始请求 /admin/users
        │
        ▼
ApplicationResolver
  ├─ Host / domain_bind
  ├─ 首段 / app_map
  ├─ deny_app_list / app_express
  └─ Resolution{name=admin, prefix=/admin, rewritten=/users}
        │
        ▼
克隆 Request + ApplicationContext
        │
        ▼
admin.Http.ServeHTTP(/users)
```

应用不存在、应用被拒绝或请求路径非法时，统一宿主分别返回 404 或 400，并且不调用任何应用的业务代码。

## 目标应用处理

目标应用的 `Http` 处理器继续执行框架内核流程：

1. 创建响应状态跟踪器并校验目标应用的 Host 白名单。
2. 冻结当前应用路由，创建 `context.Request`。
3. 把 `ApplicationContext` 写入请求对象，供控制器、服务和 URL 辅助方法读取。
4. 由目标应用解析查询参数、表单、JSON 和 multipart；请求体只消费一次，非法输入返回 400，超出目标应用的 `max_body_bytes` 限制返回 413。
5. 触发当前应用的 `HttpRun` 事件。
6. 处理项目级静态资源；动态请求继续进入应用中间件。
7. 依次执行 Recovery、Session、Trace、CSRF、语言和当前应用全局中间件。
8. 匹配当前应用路由，再执行路由中间件、控制器中间件和控制器动作。
9. 转换动作返回值为响应，处理业务错误和异常。
10. 关闭压缩流、执行 terminate、清理上传临时文件、记录访问日志并触发当前应用的 `HttpEnd`。

动态请求管道如下：

```text
ApplicationContext
      ↓
Request.Parse
      ↓
HttpRun
      ↓
静态资源判断
      ↓
Recovery -> Session? -> Trace? -> CSRF? -> 语言
      ↓
当前应用全局中间件
      ↓
当前应用路由匹配
      ↓
路由中间件 -> 控制器中间件 -> 控制器动作
      ↓
响应转换 -> terminate -> HttpEnd -> 访问日志
```

静态资源不会进入动态中间件。需要鉴权的资源不能直接放在项目 `public/` 目录中。

## 控制器分发

路由处理器可以是函数，也可以是 `Controller@Action` 字符串。字符串分发只在当前应用的控制器注册表中查找：

1. 按注册名从当前应用容器解析控制器工厂。
2. 创建新的控制器实例，避免请求之间共享可变字段。
3. 调用 `Init(app, req)`。
4. 读取控制器级中间件别名并构造控制器管道。
5. 执行动作，处理 `*context.Response`、字符串、普通值和可选 `error` 返回值。

控制器、验证器、服务和模型必须属于同一个应用边界。跨应用调用应通过明确的服务接口或 `ApplicationManager` 的应用 URL/应用查找能力完成，不能读取另一个应用的请求级状态。

## 请求结束与错误

异常恢复覆盖请求管道内的业务 panic；HTTP 内核外层恢复覆盖请求创建、响应收尾等更早或更晚阶段的 panic。错误响应提交后仍必须执行安全的资源清理，但不能把第二个错误响应追加到已提交响应中。

统一宿主的错误边界：

| 错误 | 结果 |
|---|---|
| 非法 Host、URL 转义或路径 | 400 |
| 应用不存在或被拒绝 | 404 |
| 目标应用内核配置或初始化错误 | 500，并记录应用名 |
| 路由不存在 | 404 |
| 方法不匹配 | 405，并按规则写入 `Allow` |
| 控制器动作返回业务错误 | 按异常和生产环境规则转换 |

完整路由顺序见[路由匹配](../路由/路由匹配.md)，应用选择规则见[多模块和多应用](多模块和多应用.md)，请求对象 API 见[请求](../请求响应/请求.md)。
