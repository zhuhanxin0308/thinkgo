# 可观测性

ThinkGo 提供两层可观测性能力：默认关闭的进程内 HTTP 指标注册表，以及可选注册的 OpenTelemetry OTLP/HTTP Trace Provider。两者关闭时都不会在请求热路径创建指标或 Span；分布式追踪使用独立扩展包，应用没有注册 Provider 时只保留 No-op 服务。

## 启用方式

可以在配置中开启：

```json
{
  "metrics_enable": true
}
```

也可以在应用装配阶段显式调用：

```go
metricsRegistry := app.Metrics()
metricsRegistry.Enable()
```

环境变量 `APP_METRICS_ENABLE=true` 等价于配置项。指标注册表属于当前进程中的应用实例，不能直接当作整个集群的聚合结果。

## 导出方式

启用 `app.operational_routes_enable` 后，框架会自动注册固定路径 `/__thinkgo/health/live`、`/__thinkgo/health/ready`，并在指标同时启用时注册 `/__thinkgo/metrics`。这些端点经过应用全局中间件且默认使用业务监听器，同时由以下策略控制来源：

- `operational_routes_access=restricted`：只允许 `operational_routes_allowed_cidrs` 中的来源地址；旧配置未声明白名单时仅兼容放行 `127.0.0.0/8` 与 `::1/128`，生产部署审计仍要求显式配置。
- `operational_routes_access=public`：显式公开运维端点，部署审计会给出警告；此时白名单必须为空。

来源判断只使用连接的 `RemoteAddr`，不会信任客户端可伪造的 `X-Forwarded-For`。反向代理部署应只把受信代理网段加入白名单，并由网关完成原始客户端的认证和访问控制。若要使用自定义路径或独立管理监听器，应关闭自动运维路由后显式挂载：

```go
app.Route().Get("metrics", func(*context.Request) *context.Response {
    return context.NewResponse().
        Header("Content-Type", "text/plain; version=0.0.4; charset=utf-8").
        Header("Cache-Control", "no-store").
        Content(metricsRegistry.Prometheus())
})
```

注册表也实现标准库 `http.Handler`，可在框架外的管理监听器中直接使用：

```go
http.Handle("/metrics", metricsRegistry)
```

指标只使用固定名称和低基数状态类别，不包含 URL、用户 ID、Session ID、IP 或异常文本，避免高基数和敏感信息泄露。生产环境仍应配置采集端认证、网络隔离和保留策略。

## OpenTelemetry Trace

在应用注册阶段加入 OTLP Provider：

```go
import "github.com/zhuhanxin0308/thinkgo/framework/telemetry/otlp"

if err := app.RegisterProvider(otlp.NewProvider()); err != nil {
	return err
}
```

配置结构保存在 `config/telemetry.json`，默认 `enable=false`。真实部署值由 `.env` 或系统环境变量覆盖：

```ini
[TELEMETRY]
ENABLE = true
SERVICE_NAME = orders-api
SERVICE_VERSION = 2.0.0
ENVIRONMENT = production
ENDPOINT = https://otel-collector.example.com/v1/traces
HEADERS = {"X-Tenant":"tenant-a"}
SAMPLE_RATIO = 0.1
```

`HEADERS` 是 JSON 对象字符串，因此仍是一个可由环境覆盖的配置叶子，不需要把 Collector 凭据写进 JSON 配置文件。配置解析会拒绝重复 Header、换行注入、带 URL 凭据的 endpoint、未知字段、越界采样率和不合理的队列/批次大小；配置输出会整体脱敏 `headers`。

启用后 HTTP 内核会：

- 从 `traceparent` 和 `baggage` 提取远程父上下文；
- 创建 `SpanKindServer` 的服务端 Span；
- 路由匹配后使用 `/users/:id` 这类低基数模板更新 Span 名称和 `http.route`；
- 记录 HTTP 状态码、5xx 状态和请求 panic；
- 应用关闭时在 10 秒边界内刷新批处理队列并关闭 SDK。

OTLP 扩展使用 OpenTelemetry Go 的稳定 Trace API/SDK 和 OTLP HTTP exporter。Collector 的可达性、认证、证书和后端保留策略仍是部署环境验收项；本地 Span 单测不能替代真实 Collector 验收。参考 [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/) 和 [OTLP exporter](https://opentelemetry.io/docs/languages/go/exporters/) 官方文档。

## 存活与就绪

每个 `App` 都提供独立的 `Health` 注册表。存活检查只回答进程与请求循环是否仍可服务，不探测数据库等外部依赖，失败时应由编排器重启实例；就绪检查验证数据库等依赖是否可用，失败时返回 `503`，用于把实例移出流量而不触发无意义重启。自动运维路由开启时框架会挂载固定健康路径；关闭自动路由后，应用仍可把存活和就绪处理器挂到受保护的管理路由或独立管理监听器：

```go
import (
    "context"
    "database/sql"
)

var sqlDB *sql.DB

healthRegistry := app.Health()
if err := healthRegistry.Register("database", func(ctx context.Context) error {
    return sqlDB.PingContext(ctx)
}); err != nil {
    return err
}
app.Route().Get("health/live", func(*context.Request) *context.Response {
    report := healthRegistry.Liveness()
    return context.NewResponse().Code(report.HTTPStatus()).Json(report)
})
```

`Readiness` 使用硬性总超时并按名称稳定汇总检查；即使某个检查不响应 `context.Context`，调用方也会在期限内返回。框架最多保留 4 个仍未退出的检查执行槽，持续存在的不协作检查会得到容量耗尽错误，避免无限创建 goroutine。检查函数仍必须遵守传入的 `context.Context`，及时释放连接和 goroutine。端点 JSON 只返回 `ok`/`fail` 和耗时，不返回底层错误文本，避免泄露连接串、文件路径和凭据。
