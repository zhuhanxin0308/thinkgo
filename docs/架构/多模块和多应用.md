# 多模块和多应用

ThinkPHP 的多应用模型以应用目录、应用配置和请求时应用选择为中心。ThinkGo 在 Go 的包模型上实现同样的边界：一个 Go Module 可以登记多个应用，一个进程内为每个应用创建独立 `framework.App`，再由一个 `MultiHttp` 统一监听。

## 模块、应用与宿主

- Go Module 由 `go.mod` 定义，承载框架包、应用包和多个命令入口。
- 应用是 `app/<应用名>/` 下的完整业务边界，至少拥有 `application.go` 和自己的组件目录。
- 宿主是项目级 HTTP/TLS/HTTP3 监听器，读取根 `config/` 的监听配置，不属于任一业务应用。

```text
go.mod
├── framework/
├── app/
│   ├── index/
│   │   ├── application.go
│   │   ├── controller/
│   │   ├── middleware/
│   │   ├── model/
│   │   ├── validate/
│   │   ├── lang/
│   │   └── route/
│   └── admin/
│       ├── application.go
│       ├── controller/
│       ├── middleware/
│       ├── model/
│       ├── validate/
│       ├── lang/
│       └── route/
├── config/
├── public/
├── cmd/think/
└── main.go
```

控制器、中间件、模型、验证器、多语言和路由定义不能放回 `app/` 根目录，也不能通过共享包级注册表跨应用注册。

## 应用定义

每个应用通过 `framework.ApplicationDefinition` 登记名称、目录和注册回调：

```go
framework.MustRegisterApplication(framework.ApplicationDefinition{
	Name: "admin",
	Path: "app/admin",
	Register: func(app *framework.App) error {
		// 只向 admin 对应的 app 注册组件。
		return nil
	},
})
```

通常把回调放在 `app/admin/application.go`，由应用包的 `init()` 登记定义。`ApplicationManager` 会为每个定义创建独立的容器、路由、中间件、事件和运行时路径，然后调用对应的注册回调。

`ApplicationManager` 同时拥有应用的启动、运行和关闭状态。推荐直接调用 `MultiHttp.Run()`，由宿主把 Provider 启动、路由冻结、监听和逆序关闭串成一个生命周期；不要在请求期间切换应用实例或手工并发调用 `Boot`、`Run`、`Close`。该生命周期不依赖数据库配置，也不引入分布式锁。

## 配置

应用选择配置放在项目级 `config/app.json`，也可以由环境变量或配置覆盖提供：

```json
{
    "default_app": "index",
    "app_map": {
        "backend": "admin",
        "api-v1": "api"
    },
    "domain_bind": {
        "admin.example.com": "admin",
        "api": "api",
        "*.tenant.example.com": "tenant"
    },
    "deny_app_list": ["internal"],
    "app_express": false
}
```

字段语义：

| 字段 | 作用 |
|---|---|
| `default_app` | 没有域名绑定、没有可识别路径首段时使用的应用 |
| `app_map` | 把 URL 首段映射到应用名；`*` 可作为未知首段的映射 |
| `domain_bind` | 精确域名、一级子域名键、`*.example.com` 通配域名到应用的绑定 |
| `deny_app_list` | 禁止通过路径或域名访问的已登记应用 |
| `app_express` | 未知路径首段是否交给默认应用；关闭时未知应用返回 404 |

解析优先级固定为：

```text
精确域名 / 子域名 / 通配域名
        > URL 首段的应用名或 app_map
        > app_express 回退
        > default_app
```

域名绑定请求保留完整 URL 路径；路径选择请求会移除应用首段再交给目标应用。例如 `/backend/users` 映射到 `admin` 后，`admin` 应用匹配 `/users`。

单应用且没有显式 `app_express` 配置时，为保持传统单应用访问行为，任意合法业务路径会交给默认应用；多应用项目应显式设置 `app_express`，避免未知首段被误解释为业务路由。

## 隔离边界

| 内容 | 应用目录/运行时 | 宿主项目 |
|---|---|---|
| 控制器、中间件、模型、验证器 | `app/<name>/...` | 不共享 |
| 路由加载器和路由快照 | `app/<name>/route`、`framework.ServiceRoute` | 不共享 |
| 语言和视图 | `app/<name>/lang`、`app/<name>/view` | 不共享 |
| 配置覆盖 | `app/<name>/config` | 根 `config/` 先加载 |
| 日志、缓存、Session | `runtime/<name>/` | 不共享文件目录 |
| `public/`、异常模板 | 不随应用切换 | 项目级共享 |
| 监听地址、端口、TLS、HTTP/3 | 不能覆盖 | 根 `config/` 唯一来源 |

应用级配置可以覆盖本应用业务配置，但不能修改统一宿主的监听边界。`MultiHttp` 创建内部 `Http` 时会校验各应用的服务器配置一致；不一致会在监听前返回错误。

`config/database.json` 是可选的。文件缺失表示该应用不启用数据库连接，`framework.ServiceDBManager` 仍会创建为无连接的安全占位，`framework.ServiceDB` 不可解析，缓存、路由、模板和 HTTP 处理仍可用；文件存在但格式或连接配置错误时，错误会保留在启动状态并阻止宿主监听。

## 请求与 URL

请求应用选择由 `ApplicationResolver` 完成，并生成不可变的 `ApplicationContext`。上下文保存应用名、原始路径、重写路径、路径前缀、Host 和域名绑定状态。

在请求中生成 URL 时使用：

```go
url := app.URLFor(req, "/login")
routeURL, err := app.RouteURL(req, "user.show", map[string]interface{}{"id": 10})
adminURL, err := app.URLForApplication(req, "admin", "/dashboard")
```

当前应用会自动恢复被宿主移除的路径前缀；域名绑定应用使用请求 Host；跨应用 URL 使用目标应用的域名绑定、`app_map` 别名或应用名。用户输入不能直接作为应用名、Host 或路径拼接使用。

多应用转发只复制请求元数据。克隆请求与原请求共享一次性 `Body`，`MultiHttp` 不预读、不复制、不提前关闭请求体；目标应用负责按自己的 `max_body_bytes` 解析并在消费完成后关闭。这样可以保留流式上传语义，也避免同一请求在多个应用之间被重复消费。

## 选择部署模式

| 模式 | 特征 | 适用场景 |
|---|---|---|
| 单应用 | 只登记 `index`，仍使用 `ApplicationManager` 和 `MultiHttp` | 默认站点、平滑迁移旧项目 |
| 同进程多应用 | 多个 `ApplicationDefinition`，一份监听器，按域名或路径分发 | 前台、后台、API 共用端口 |
| 多进程 | 每个命令或 Module 独立运行 | 强隔离、独立发布或不同监听配置 |

同进程多应用适合共享框架和监听器的场景；需要不同端口、不同 TLS 身份或不同进程权限时，应拆成多个入口或进程，而不是在请求期间修改同一份宿主配置。

## 安全约束

- 应用名、应用映射别名和域名绑定在启动时校验，不能包含路径穿越、控制字符或未定义目标。
- URL 中的 `%2f`、`%5c`、`%2e%2e` 和 `%00` 等编码路径在应用选择前拒绝。
- `deny_app_list` 不能拒绝 `default_app`，域名绑定不能指向被拒绝或未登记应用。
- 原始请求不被解析器修改，目标应用只处理克隆请求。
- 应用注册回调不能保存另一个应用的容器、请求或控制器实例。
