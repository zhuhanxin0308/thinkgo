# 容器和依赖注入

ThinkGo 的 `framework.Container` 负责绑定和解析应用依赖。`framework.App` 持有独立容器，应用可以通过 `app.Bind`、`app.BindFactory`、`app.BindScoped`、`app.Instance` 和 `app.Make` 管理服务，同时保持依赖关系显式可测试。

每个编译期应用拥有独立容器。应用注册回调必须使用框架传入的 `app`，不得把 App、Request、容器或“当前应用名”保存为可变包级对象；请求级依赖使用该应用容器创建的显式作用域隔离。

## 绑定方式

| API | 生命周期 | 适用场景 |
|---|---|---|
| `Bind` | 单例，首次解析后缓存 | 配置、日志、外部客户端等应用级服务 |
| `BindFactory` | 工厂，每次解析重新创建 | 控制器、一次性命令对象和有独立状态的对象 |
| `BindScoped` | 同一请求或任务作用域复用，作用域之间隔离 | 工作单元、请求跟踪器和请求级外部资源 |
| `Instance` | 已创建实例的单例 | 将应用已初始化的能力放入容器 |

绑定名称是当前容器内的唯一标识。重绑定会使旧实例和正在进行的旧构建失效，删除绑定使用 `Delete`，查询是否存在使用 `Has`。

## 注册单例服务

```go
type Mailer struct {
	config interface{}
}

func NewMailer(config interface{}) *Mailer {
	return &Mailer{config: config}
}

app.Bind("mailer", func(container *framework.Container) (interface{}, error) {
	config, err := container.Make("mail.config")
	if err != nil {
		return nil, err
	}
	return NewMailer(config), nil
})

mailer, err := app.Make("mailer")
if err != nil {
	return err
}
_ = mailer
```

工厂可以通过注入的容器继续解析依赖。工厂必须返回实例，或者返回 `(实例, error)`；返回值数量、第二个返回值类型和工厂执行 panic 都会被容器校验并转换为错误。

工厂解析依赖时必须使用工厂参数中的容器，不要闭包捕获外层容器后递归解析：

```go
type Reporter struct {
	logger interface{}
}

app.Bind("reporter", func(container *framework.Container) (interface{}, error) {
	logger, err := container.Make("log")
	if err != nil {
		return nil, err
	}
	return &Reporter{logger: logger}, nil
})
```

## 工厂服务

需要每次解析都获得新对象时使用 `BindFactory`：

```go
type RequestContext struct{}

app.BindFactory("request_context", func() interface{} {
	return &RequestContext{}
})
```

控制器注册会自动使用工厂绑定。HTTP 内核每次解析控制器时都会创建新的控制器实例，避免请求级字段被并发请求共享。

控制器由 `app/<应用名>/autoload_generated.go` 自动发现并使用工厂绑定。把导出控制器放在 `app/<应用名>/controller` 后，该应用路由中的 `user/index` 会从目标应用请求作用域创建新的 `User` 实例；同名控制器可在其它应用独立存在。

不要把请求对象、响应对象、控制器实例或请求级 Session/Cookie 绑定为单例。跨中间件传递请求数据应使用 `req.Set` 和 `req.GetData`，而不是写入容器或包级变量。

## 请求和任务作用域

需要在一次请求内共享、在请求之间隔离并在请求结束自动释放的服务使用 `BindScoped`：

```go
type UnitOfWork struct{}

func (work *UnitOfWork) Close() error {
	return nil
}

app.BindScoped("unit_of_work", func() interface{} {
	return &UnitOfWork{}
})
```

HTTP 路由、中间件和控制器可以从当前请求解析。相同名称在同一请求中返回同一实例；实现 `io.Closer` 的作用域实例会在终止中间件执行后按创建逆序关闭：

```go
service, err := req.Make("unit_of_work")
if err != nil {
	return context.NewResponse().Code(http.StatusInternalServerError)
}
_ = service
```

后台任务必须显式创建和关闭作用域：

```go
scope, err := app.NewScope()
if err != nil {
	return err
}
defer scope.Close()

service, err := scope.Make("unit_of_work")
```

根容器不能直接解析 `Scoped` 绑定。单例也不能直接或通过工厂间接依赖 `Scoped` 服务，否则会返回 `ErrScopedDependencyCaptured`，避免把首个请求的实例泄漏到后续请求。

## 解析 API

- `Make(name, params...)` 返回 `(interface{}, error)`，用于业务路径和需要显式处理失败的启动路径。
- `Get(name)` 是必需成功版本，解析失败会 panic，只适合绑定已由启动阶段保证存在的依赖。
- `Has(name)` 判断绑定或显式实例是否存在。
- `Delete(name)` 删除绑定与实例，并使对应在途构建失效。
- `NewScope()` 创建显式请求或任务作用域；`ContainerScope.Close()` 幂等释放作用域资源。

容器会检测循环依赖并返回错误。并发解析同名单例时只允许一个工厂构建，其它解析等待同一结果；不同依赖链形成锁等待时会返回循环依赖错误，避免死锁。

## 显式实例

应用初始化完成或由调用方替换的能力可以通过 `Instance` 绑定。框架服务的名称使用 `framework.Service*` 常量，避免业务代码散落字符串：

```go
app.Instance(string(framework.ServiceCache), cache)

resolved, err := framework.ResolveServiceAs[*cache.Cache](app, framework.ServiceCache)
if err != nil {
	return err
}
_ = resolved
```

同名 `Instance` 会覆盖原有绑定并使旧构建失效，同时同步应用内部的服务快照。缓存、数据库、日志等框架托管资源的关闭责任由应用生命周期管理，不应在请求处理期间随意关闭容器中的共享资源。应用 `Close` 会处理替换前后的受管实例，避免只关闭当前实例造成资源泄漏。

普通业务使用 `app.Cache()`、`app.Log()`、`app.DB()` 等直接入口。`ResolveServiceAs[T]` 只用于框架扩展需要按服务名校验替换实现的场景：

```go
logger, err := framework.ResolveServiceAs[*log.Log](app, framework.ServiceLog)
if err != nil {
	return err
}
logger.Info("服务已装配")
```

自定义服务可以使用 `TypedServiceKey[T]`，让绑定和解析共享同一类型契约，避免名称相同但调用方类型不一致：

```go
mailerKey, err := framework.NewTypedServiceKey[*Mailer]("mailer")
if err != nil {
	return err
}
if err := framework.BindTyped(app, mailerKey, func(container *framework.Container) (*Mailer, error) {
	return NewMailer(container), nil
}); err != nil {
	return err
}

mailer, err := framework.ResolveTyped(app, mailerKey)
```

对应生命周期分别使用 `BindTyped`、`BindFactoryTyped`、`BindScopedTyped`；已创建实例使用 `InstanceTyped`。`ResolveTyped` 接受实现 `Make` 的应用、容器、请求或显式作用域，并在运行时拒绝类型不匹配、空实例和类型化空解析器。

## 依赖注入边界

- 优先通过构造函数或应用服务工厂接收依赖，不在业务方法中创建新的全局单例。
- 服务层只依赖完成业务所需的接口或应用能力，不把整个容器传播到所有方法。
- 控制器由容器工厂创建，控制器中的请求状态只保存在当前请求实例。
- 应用服务的 `Register` 阶段适合绑定服务和监听器，启动依赖关系由 `Boot` 阶段处理，具体见[服务](服务.md)。
- 容器错误必须向上传播或转换为明确的启动/业务错误，禁止吞掉解析失败。

容器是应用组合根的一部分，不是绕过分层的全局服务定位器。完整应用生命周期见[架构总览](架构总览.md)，请求级状态边界见[请求流程](请求流程.md)。
