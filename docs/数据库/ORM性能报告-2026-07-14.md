# ORM 性能报告（2026-07-14）

本报告记录 ThinkGo ORM 修复后的可重复基准、profile、真实驱动边界和优化取舍。所有 MySQL 基准只访问 `bench_orm_` 前缀表，凭据仅从当前进程环境变量读取；未新增配置文件。

## 基线环境

- Go/OS/Arch：`go1.26.5 windows/amd64`，基准命令显式设置 `CGO_ENABLED=1`。
- CPU：AMD Ryzen 5 7500F 6-Core Processor（12 逻辑线程）。
- SQLite：CGO `github.com/mattn/go-sqlite3 v1.14.47`，每个子基准使用独立内存库和真实 SQL。
- MySQL：本机 MySQL Community Server `8.0.30`，`github.com/go-sql-driver/mysql v1.10.0`。
- MySQL 隔离边界：每轮生成带进程号和纳秒时间戳的唯一 `bench_orm_users_*` 表，deterministic seed 100,000 行，结束时自动 `DROP TABLE`；不清空或复用调用方已有表。
- MySQL 实测参数：20 GiB InnoDB buffer pool、`max_connections=512`、`innodb_flush_log_at_trx_commit=2`、`sync_binlog=0`。
- 原始输出：本机 `runtime/orm-baseline-sqlite.txt`、`runtime/orm-baseline-mysql.txt`，文件不提交且不包含凭据或完整 DSN。

## 2026-07-28 优化后复测

本轮在同一 Windows amd64 工作站上完成了条件构造、关系索引、游标分页、深分页、结果物化和真实 MySQL CRUD 复测。SQLite 基准使用 `-benchtime=300ms -count=5`，MySQL CRUD 使用 `-benchtime=2s -count=5`；表名按进程和纳秒时间戳隔离，结束后自动清理。

| 场景 | 中位 time/op | B/op | allocs/op |
|---|---:|---:|---:|
| `WhereFields` Query/1,000 | 61.2 µs | 49,184 | 1,003 |
| `WhereFields` Model/1,000 | 80.0 µs | 49,232 | 1,004 |
| `RelationIndex`/10,000 parents × 4 | 2.80 ms | 2,128,360 | 30,081 |
| `SeekPage`/100,000 | 0.82 ms | ≈442.9 KB | 7,104 |
| `SeekPage`/1,000,000 | 0.75 ms | ≈442.9 KB | 7,104 |
| OFFSET/1,000,000 | 7.56 ms | ≈446 KB | 7,095 |
| keyset/1,000,000 | 0.68 ms | ≈444 KB | 7,110 |
| SQLite 结果物化/100,000 | 60.32 ms | 46,087,752 | 699,813 |
| SQLite `Column` 专用列扫描/100,000 | 26.63 ms | 12,120,812 | 200,079 |

相对本轮优化前的同机结果，1,000 条条件链约从 `0.28 ms / 118.9 KB / 3,023 allocs` 降至 `0.061 ms / 49.2 KB / 1,003 allocs`；10,000 主记录关系索引约从 `4.2 ms / 2.77 MB / 109,685 allocs` 降至 `2.8 ms / 2.13 MB / 30,081 allocs`。`SeekPage` 的延迟基本稳定，但整数游标路径的分配已从约 7,113 次降至约 7,104 次。

真实 MySQL CRUD 当前有效五轮中位结果为：并发 1 约 `0.661 ms / 12,155 B / 191 allocs`，并发 32 约 `0.189 ms / 12,193 B / 191 allocs`，并发 256 约 `0.551 ms / 13,095 B / 197 allocs`；三档连接池等待均为 0。延迟受本机数据库调度和 I/O 波动影响，不作为生产容量承诺。

profile 表明真实 MySQL CRUD 的 CPU 主耗时在 `runtime.cgocall`、`database/sql` 和 MySQL 驱动写包路径，分配热点集中在数据行复制、查询对象构造与结果物化。针对标量复制反射路径的 A/B 没有稳定端到端收益且增加分配，未保留该改动；当前单条件 `Predicate` 已跳过重复的占位符扫描，profile 前 25 个热点中不再出现正则扫描，但端到端分配量基本不变。当前更值得继续关注的是减少不必要的结果列和往返次数。

本轮新增 SQL `Column` 专用列扫描：100,000 行相对完整行物化约减少 74% 内存、71% 分配，延迟约降低 56%；真实 MySQL 已通过同规模列扫描回归。模型层新增 `Each` 流式入口，关联预加载会明确拒绝；`Chunk/ChunkById` 在 SQL 连接上多读一行判断后续批次，避免精确整批结束时的空查询，非 SQL 连接保持原有分页语义。

本轮 `interpolateParams=true` 与默认预编译路径的 A/B 结果没有显示收益：并发 1/32/256 的中位延迟分别约慢 `53.9%/169.4%/65.8%`。样本只有五轮且未形成 95% 置信区间，因此结论限定为当前环境：不应据此开启该选项，生产仍需独立压测。

|---|---:|---:|---:|

## 真实 MySQL 基线

每个操作执行真实的 Insert → 主键 Select → Update → Delete，使用固定数量 1/32/256 个 worker；十轮、每组 `-benchtime=3s`。表中 `ns/op` 为聚合吞吐口径，不等同于单请求端到端延迟。

| 并发 | median ns/op | mean B/op | mean allocs/op | pool waits/op |
|---:|---:|---:|---:|---:|
| 1 | 1,144,675 | 12,601 | 226 | 0 |
| 32 | 385,738 | 12,632 | 226 | 0 |
| 256 | 350,744 | 13,049 | 229 | 0 |

32 并发相对单 worker 的聚合处理率明显提高；256 并发中位吞吐仅继续改善约 9%，且运行间方差上升。`DB.Stats()` 十轮均为 0 pool wait，因此当前数据不支持修改框架通用连接池默认值；瓶颈位于服务端/网络/调度与四次往返组合，而不是客户端连接获取等待。

- 按 `reflect.Type` 缓存不可变字段元数据；缓存构建时完成标签解析、标识符、选项和重复列校验。
- 生产转换只读内部不可变快照；诊断入口返回 slice 副本，调用方不能污染 cache。
- Getter 注册时重建按字段排序的不可变快照；查询行只复制 slice header，不再逐行复制 map 和排序。

### 行扫描分配

1000/10000/100000 行各 10 秒的 alloc-space profile 共采样 39296.42 MB：

| 函数 | flat | cumulative |
|---|---:|---:|
| `scanRows` | 86.32% | 99.71% |
| `go-sqlite3._Cfunc_GoStringN` | 6.85% | 6.85% |
| `go-sqlite3.(*SQLiteRows).nextSyncLocked` | 6.53% | 13.38% |

`scanRows` 明确是分配热点。优化后每个结果集只创建一组 `values`/`scanArgs`，每行扫描前清空槽位；返回 map 仍逐行创建，`[]byte` 仍逐值复制。复用 backing buffer 的测试驱动验证修改任一返回行不会影响其它行。

关系索引从 1,000 到 10,000 父行的时间/空间近似线性增长，没有出现平方级退化。100,000 行时深 OFFSET 比 keyset 慢约 1.64 倍；1,000,000 行时扩大到约 9.50 倍，而 keyset 保持在约 0.9 ms。框架不会把 `Chunk` 自动改写为 keyset：调用方没有声明唯一、非空、严格递增游标前，自动改写会改变结果完整性；需要大数据遍历时应显式使用 `ChunkById` 和已注册的 `CursorCodec`。

## MongoDB 与 Neo4j live 边界

新增 `integration` build tag 的隔离 harness：资源名包含 `bench_orm_`、进程号和随机后缀；Mongo 使用独立集合，Neo 使用独立 label，cleanup 只删除本轮资源。Mongo 覆盖真实 `InsertedID`、十六进制 `_id` 往返、matched/modified 和投影；Neo 覆盖严格删除失败、显式 detach 以及节点/关系统计。live benchmark 覆盖：

- Mongo：10,000/100,000 行 × 并发 1/32/256 × 全量物化/深 skip/已转义 regex，共 18 组。
- Neo4j：10,000/100,000 行 × 并发 1/32/256 的 managed-session collect，共 6 组。

本机执行结果：

| 项目 | 状态 | 原因 |
|---|---|---|
| `TestLiveMongoOperationContract` | SKIP | `THINKGO_LIVE_MONGO_*` 未配置 |
| `TestLiveNeoStrictAndDetachDelete` | SKIP | `THINKGO_LIVE_NEO4J_*` 未配置 |

因此没有对 Mongo cursor 物化、Neo session 吞吐或 NoSQL 连接池参数做生产优化；这些候选必须等待真实服务 profile。当前状态只能写 `fixed + live-driver pending`，不能写 live PASS。

## 独立源码复审

独立审查在阶段性实现后发现 NQ-09：Mongo Model 默认逻辑 `id` 没有与固有 `_id` 完整回环。`add0b2b` 修复默认映射，随后审查继续定位显式业务主键零值和不可变主键更新两个边界；`bdf4ca3` 在驱动写入前分别返回 `ErrInvalidModel` 和 `ErrInvalidQuery`，并增加官方 Mongo mock command monitor 断言。

最终复审结论为 **ACCEPT**：Critical 0、Important 0、Minor 0。复审单独验证了 Mongo/Model/Neo 定向 race、全部 `framework/db/...`、Oracle tag 和 `go vet`；Mongo live harness 因未配置 `THINKGO_LIVE_MONGO_*` 明确 SKIP。该结论不把未运行的真实 MongoDB/Neo4j 服务端矩阵写成通过。
