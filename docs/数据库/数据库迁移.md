# 数据库迁移

迁移定义属于具体应用实例，不使用进程级全局列表。每个应用拥有独立迁移 Registry 和数据库配置；CLI 通过 `--app` 选择目标，省略时使用 `app.default_app`。

## 注册 SQL 迁移

```go
current, err := migration.NewSQL(
    "202608150001_create_users",
    []string{"CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(120) NOT NULL)"},
    []string{"DROP TABLE users"},
)
if err != nil {
    return err
}
return app.RegisterMigration(current)
```

每个 SQL 切片元素由驱动独立执行；框架不按分号拆分，避免破坏触发器、过程和字符串。名称以 12 至 20 位时间序列开头，后接下划线和小写标识。迁移放在 `app/<name>/migration` 或应用服务中注册，不能注册到项目级可变全局列表。

程序化迁移使用 `migration.New` 并提供稳定 SHA-256。修改已发布迁移会触发校验和阻断；应新增迁移，不覆盖历史。

## 执行与检查

```bash
go run ./cmd/think migrate --app admin
go run ./cmd/think migrate:status --app admin
go run ./cmd/think migrate:rollback --app admin --batches 1
```

- `migrate` 按名称升序执行待处理项，同次命令共享批次号。
- `migrate:rollback` 按批次倒序、批次内按名称倒序回滚。
- `migrate:status` 校验历史后展示状态。
- 历史表 `thinkgo_migrations` 记录名称、SHA-256、批次和 UTC 时间。
- 缺少代码定义、重复名称、非法批次或校验和漂移都会阻断操作。
- 每个迁移的业务操作与历史写入使用同一事务；事务性 DDL 能力仍取决于数据库方言。

`deploy:check` 未指定 `--app` 时对全部编译期应用执行只读迁移检查，不创建历史表。任何应用存在待执行迁移或未初始化历史都会阻断部署。
