# 内存缓存：容量、到期回收与资源边界

`driver.NewMemoryWithMaxEntries(n)` 限制的是计入容量的记录数量，不是堆内存字节数。`NewMemory()`、容量为零和零 TTL 的既有行为保持不变：容量零不限制条目，TTL 零不自动过期。应用默认缓存驱动与直接创建内存驱动是不同选择，不能把这项能力描述为所有应用默认获得内存预算。

本文描述兼容构造器的 FIFO 行为。需要单值图、累计计费量、全部条目和锁的准入边界时，使用 [`NewMemoryWithBudget`](memory-cache-budget.md) 并配置业务 TTL；严格预算采用超限拒绝策略。

## 满容量时的规则

新增条目会先检查是否有已到期的计费条目；存在时，在同一写锁内回收，再决定是否拒绝或淘汰。不需要业务先读取过期键，也不必等到下一次一分钟周期清理。TTL 边界使用 `now >= expiry`，判断发生在提交路径中，因此原子更新回调期间过去的时间也被考虑。

未到期业务记录继续采用原有 FIFO 淘汰顺序；未到期受保护的标签元数据不可为了新条目而淘汰，仍占容量。全被活跃受保护记录占用时，继续返回 `ErrMemoryCapacityExhausted`，不会伪装成功或清除同步状态。fencing 元数据的原有容量豁免与独立锁空间保持不变。`Clear` / `ClearPrefix` 仍保留 fencing 记录，不会释放活跃锁。

内部计数在新建、删除、淘汰、惰性读取、原子删除、前缀清理和全量清理时同步更新，不再为每次容量查询遍历整个 map。最早到期时间采用保守提示；覆盖或删除后提示可能偏早，但不能偏晚。容量压力下必要的一次扫描会重建该提示。周期数据清理和锁清理仍按原有周期进行，压力下的数据清理不推迟锁清理。

## 没有提供的保证

条目数不是总内存、单对象大小、请求并发或进程资源上限。任意 map、slice、指针和循环对象仍可能在输入、缓存快照和返回副本中占据较大空间；容量豁免的同步元数据与锁也有独立资源消耗。本修补不新增对象图字节预算，不调整默认 TTL，不启动后台清扫 goroutine，也不承诺闲置时立即归还过期值的堆内存。

业务须按实际负载选择容量与 TTL，并在调用前限制键和值的规模，限制并发和同步元数据基数，配合进程资源限制与观测。严格对象图计费与复制规则见[资源预算](memory-cache-budget.md)；其准入配额也不能代替进程内存与请求并发上限。

## 验证入口

`memory_capacity_expiry_test.go` 使用 `testing/synctest` 推进虚拟时间，断言七种写入入口在容量压力下优先回收过期项；检查有效 FIFO、受保护项、fencing 与锁隔离，以及全部计数变更路径和并发一致性。模糊测试用独立 map 计数核对内部计数，覆盖清理及时间推进。

`BenchmarkMemoryCapacityInsertFull` 排除预填充与键格式化时间，使用固定标量、无 TTL、满容量业务写入对比容量核算开销。该基准不证明 HTTP 吞吐量，也不覆盖所有含保护元数据或大量到期项的工作负载；到期回收和跳过受保护 FIFO 节点仍可能遍历记录。
