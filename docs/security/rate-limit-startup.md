# 生产 HTTP 启动限流提示

内置 `rate_limit` 继续保持显式启用。统一限流阈值不能替代应用的容量规划、账户维度防撞库或网关策略；本项不为所有应用强制启用同一个速率。

## 框架新增的检查

HTTP 内核完成应用准备和 Provider Boot、取得最终服务快照后，检查运行环境与 `rate_limit.enable`。环境为 `production`、`prod` 或 `release` 时（忽略大小写和首尾空格），配置缺省或显式为 `false` 会产生 Warning 级提示：

> 生产环境未启用内置 rate_limit 配置；请确认网关或敏感路由已配置合适的限流策略

结构化字段包括 `code=rate_limit_disabled`、`configuration=rate_limit.enable`、`scope=http` 和 `phase=startup`，不记录请求、凭据或配置值。

这是配置提示，不是启动错误，不修改中间件管线、状态码、默认阈值、缓存后端或故障处理策略。现有非法配置和其他生产安全检查继续按原有规则阻止启动。开发/测试环境不产生此提醒，合法的 `enable=true` 配置也不产生此提醒。

## 时机与日志可见性

检查接入 HTTP 的一次性初始化以及运行租约获取后的服务重新发布，不在每个请求中扫描配置。嵌入式 `ServeHTTP` 在首次初始化时触发；命令行任务不因本项新增限流要求。

每个 HTTP 内核对连续相同的日志服务只提示一次。合法替换最终日志服务后，新日志器仍收到一次提示；只保存最近的日志器，不维护无界历史。多个应用内核各自检查自己的有效配置。日志器为空不消耗提示机会，调用自定义日志代码时不持有去重锁。

日志关闭、级别过滤、自定义驱动丢弃或输出失败仍可能使提示不可见；本项不把日志投递成功当作服务启动前置条件。已有网关/业务限流的部署可以根据固定 `code` 分类处理日志，但应保留相应的部署和回归证据。

## 应用仍需明确的策略

出现此提示不证明应用没有任何限流；没有提示也不证明业务已得到充分保护。此检查无法验证网关是否可被绕过、Provider 是否替换了中间件、所有敏感路由是否接入限流，或多个实例是否共享计数。

按账户、受信代理解析后的来源地址及必要的资源维度设计限额；说明匿名与登录用户的处理、存储容量、分布式计数、取消、故障时放行或拒绝以及误伤恢复。密码哈希的计算预算与请求限流也不是同一个控制。

启用框架内置策略时使用现有 `config/rate_limit.json` 的 `enable`、`rate`、`period_seconds`、`burst`、`max_keys` 字段，并在部署负载下选择值。默认值不作为适用于所有应用的安全承诺；既有显式策略的 429 行为保持不变。

## 回归边界

测试通过真实 HTTP 内核覆盖两种安全 profile、缺省/关闭/开启配置、正常请求与显式策略的 429，以及环境别名、并发去重和最终日志器重绑定。它不冒充真实网关或多实例存储验证。完整仓库 CI 和实际合并后的主分支验证仍是 issue 关闭条件。
