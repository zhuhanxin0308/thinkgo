# HttpRun 事件的作用域与安全检查

关联 issue #33。本项补齐错误放置监听器的诊断，不改变事件顺序，也不自动把应用监听器提升为项目监听器。

## 哪些监听器会执行

`HttpRun` 的真实事件名是 `framework.HttpRun`。HTTP 内核在全局中间件和应用解析之前，调用 `DispatchProjectContext`，只执行项目级监听器。`ListenApplicationEvents` 以及 `SubscribeApplication` 注册的监听器不会在这个阶段执行，单应用部署也不例外。应用通配监听器仍可正常接收后续的适用事件，例如 `HttpEnd`。

`HasListener("HttpRun") == true` 只表示存在匹配项，不代表项目级分发会执行其中每一项。新增 `HasApplicationListener` 可检查是否存在匹配的应用级项，沿用注册别名、精确匹配和通配规则；查询不会调用监听器，且结果仅是并发安全的瞬时快照。订阅回调失败、事务回滚及句柄移除不会留下虚假匹配。

## 启动期诊断

完成 App 初始化与 Provider Boot 后，HTTP 内核检查实际发布的事件服务和日志服务。若存在匹配 HttpRun 的应用级监听器，使用配置的日志器记录 warning：

> 应用级 HttpRun 监听器不会在请求开始阶段执行；请使用项目级监听器或全局中间件

每个 HTTP 内核最多记录一次。多应用的子内核分别检查自身事件表；监听租约固定服务后的重新发布也执行检查，但不会重复该内核的告警。尚未匹配监听器或缺少日志器不会消耗告警机会。不会在每次请求中扫描事件表或写入同一条警告，也不会执行尚未具备应用上下文的回调。

日志沿用现有级别过滤、缓冲及错误处理规则：主动关闭 warning、日志丢弃或输出失败时，不能保证操作者收到提示。它不是启动拒绝策略，也不是安全控制本身。应用应在支持的注册/Boot阶段完成配置；直接绕过 App 生命周期、在运行期间修改 Dispatcher 不在启动诊断的保证范围内，可显式调用查询方法检查。

## 安全检查应该放在哪里

身份认证、WAF、限流和拒绝请求的检查应使用全局中间件或合适的项目级监听器；需要请求对象、路由身份或租户权限的判断，应选择拥有这些数据的中间件阶段。普通应用事件和 HttpEnd 不等于请求入口安全拦截器。不能因为收到告警，就不加区分地把依赖应用上下文的回调提前执行。

项目级回调返回错误仍沿用既有 HTTP 异常处理，应用级 HttpRun 回调仍不执行。`HasApplicationListener` 的公开调用示例见 `event/application_listener_example_test.go`。

## 验证

```sh
go test -race -shuffle=on -count=20 -run '^TestIssue33' ./event ./http
go test -run '^ExampleDispatcher_HasApplicationListener$' ./event
```

回归覆盖直接注册、内置/自定义别名、通配、订阅者、失败事务、移除后的查询以及并发读写；HTTP测试检查启动前后日志、服务重新发布、重复请求和原生多应用的实际分发次数。日志驱动使用可观测测试实现，不声称验证所有外部日志后端。
