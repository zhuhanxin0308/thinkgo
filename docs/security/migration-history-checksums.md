# SQL 迁移历史校验和：方向边界与升级

`NewSQL` 的历史摘要绑定规范化后的 Up/Down 语句序列，用于 Runner 对照已应用历史和恢复日志；它不是作者签名，也不能批准首次收到的代码。首次执行准入仍参见[独立批准清单](migration-trust.md)。本修补不启用全局批准策略，不改写任何历史表，也不改变 SQL 的可执行语法。

## 受影响范围

旧编码使用 `up\0`、各条 Up 语句加 NUL、`down\0`、各条 Down 语句加 NUL。语句自身不得包含 NUL，但完整语句 `down` 与方向分隔标记的编码相同。例如：

```text
A.Up   = ["SELECT 1"]
A.Down = ["SELECT 2", "down", "SELECT 3"]
B.Up   = ["SELECT 1", "down", "SELECT 2"]
B.Down = ["SELECT 3"]
```

两份定义在旧实现中产生完全相同的哈希输入。这是结构编码歧义，不是攻破 SHA-256。触发的是 `strings.TrimSpace` 规范化后的一整条语句恰好等于小写 `down`；`DOWN`、`down;`、`EXEC down`、注释或字符串里包含 `down` 不属于该编码歧义。这里不对各数据库的语法有效性做推断，框架也不通过拒绝存储过程调用来掩盖问题。

## 当前编码与兼容性

不含完整 `down` 语句的定义继续使用原编码，历史摘要逐字保持不变。其 NUL 分词中只有一个 `down` 方向分隔标记，Up/Down 边界可以唯一确定。

任何一组中出现完整 `down` 语句时，整个定义使用以下 v2 哈希输入：

```text
text("thinkgo/sql-migration-history/v2")
text("up"),   uint64(len(Up)),   text(Up[0]),   ...
text("down"), uint64(len(Down)), text(Down[0]), ...
```

`uint64` 是 8 字节大端无符号整数；`text(s)` 是 `uint64(len(s))` 后接 s 的原始字节。语句已按原规则去除首尾空白，不执行大小写折叠或 UTF-8 替换。空 Down 和 nil 等价，Up 至少一条。完整用途域、两组方向、语句数量、顺序和字节边界均参与 SHA-256。

v2 输入以用途域长度开始，与旧输入固定的 `up\0` 前缀分离。未受影响定义的旧编码本身可唯一解码，受影响定义的 v2 编码带明确数量及长度，两类输入不会发生原来的边界串接混淆。

存储输出仍是 **64 位小写十六进制 SHA-256**，不增加字段或外部版本前缀。版本固定在哈希输入中，不能仅从摘要外观识别版本；需要检查独立可信的原始 SQL 定义。`Migration.Checksum()` 仍是内容标识，迁移名称由既有历史记录另行关联，不能把它当成绑定名称的批准摘要。`SQLApprovalDigest` 的独立 `sql-approval-v1` 格式、名称绑定及既有值不变。

| 写入方与历史 | 当前读取方 | 结果 |
| --- | --- | --- |
| 旧版写入、普通定义 | 当前相同定义 | 摘要不变，正常读取、应用和回滚 |
| 当前写入、普通定义 | 旧版相同定义 | 摘要不变，存储协议保持兼容 |
| 旧版写入、含完整 `down` 的定义 | 当前相同或另一份歧义定义 | `ErrMigrationDrift`；不得回退到旧摘要放行 |
| 当前 v2 写入、含完整 `down` 的定义 | 当前相同定义 | 使用 v2 摘要正常校验；SQL 执行仍由数据库决定 |
| 当前 v2 写入、含完整 `down` 的定义 | 旧版定义 | 旧版计算出的摘要不同，不能将代码回滚视为无条件兼容 |

`Status`、`InspectStatus`、`Apply`、`Rollback`、`ResolveDirty` 都保留严格摘要相等检查。受影响旧记录即使与当前源代码“看起来相同”也会拒绝：一个歧义旧摘要不能证明最初执行的是哪一份方向定义。只读检查不会修复它，`ResolveDirty` 不是摘要重签工具。拒绝不会执行该迁移的 Up/Down 或改写其历史/journal；既有写锁获取可能推进 fencing token，不应把它误称为整个数据库零写入。

## 升级前检查与受影响记录处理

部署前从独立可信的历史发布源码核对所有 SQL 迁移，查找规范化后完整等于 `down` 的元素；不要仅搜索 SQL 内的子串。普通定义不需要重算或回填历史表。受影响定义应在预发布检查中显式报告，并在完成专门恢复方案前停止该数据库的迁移写入。

对于已经存在歧义旧记录的数据库：先停止全部新旧迁移写入者并保留数据库及历史/journal 备份，再独立确认原始 Up/Down、批准清单、实际 schema 和已经发生的数据副作用。只有经过人工核准、针对该数据库制定并演练的恢复流程才可重建可信历史；不能根据“当前代码的旧摘要也相同”直接批准它，更不能从刚收到的 SQL 自动生成批准清单。

该补丁**不提供自动重签或通用 UPDATE 脚本**。若专门恢复方案需要调整元数据，必须在持锁、可审计的数据库边界内核对原名称、批次、摘要、journal 操作和状态，并保持历史与 journal 一致；不能删除历史以强迫重跑 Up，也不能只修改其中一张表。实际数据状态与元数据不同的情况必须先处理，不可用 `ResolveDirty` 强行抹除漂移。

混合版本部署不能让旧节点继续执行尚未被安全编码保护的定义。普通定义可以按既有流程回滚应用二进制；受影响定义产生新历史后，回滚必须同时考虑摘要不匹配和数据库实际状态。该补丁不替操作员作来源认证或数据恢复决定。

### 每个数据库的恢复交付记录

恢复方案应针对一个明确的数据库／schema，至少记录以下证据；仅添加审批摘要或升级应用二进制不满足这些条件。

| 记录 | 核验目标 |
| --- | --- |
| 可信历史发布源码及来源凭据 | 独立确定最初的迁移名称、Up/Down、语句顺序；不能以当前源码的旧摘要相等代替 |
| 全部迁移写入者及停止记录 | 覆盖旧版节点、当前节点、定时任务和人工工具，避免恢复时再次写入 |
| 数据库身份、备份及原始 history/journal 快照 | 固定名称、摘要、批次、操作、状态和 fencing token，并证明备份可恢复 |
| 实际 schema、数据及副作用核验 | 区分已应用、部分应用、已回滚以及无法确定的状态；包括相关触发器、过程和外部副作用 |
| 获准的数据库专用恢复步骤 | 明确锁／维护窗口、元数据变更前置条件、history 与 journal 的一致更新和失败后的恢复方式 |
| 副本演练与恢复后只读检查 | 在隔离副本上执行同一方案，复核预期数据状态；对目标新二进制运行 `InspectStatus`，完整校验历史及 journal |
| 重新开放写入及二进制回滚条件 | 确认全部写入者采用兼容实现；受影响 v2 历史不会被旧版摘要接受，单独演练需要的应用回滚方案 |

缺少独立原始定义、无法核实实际副作用、history/journal 不一致或无法排除并发写入时，继续停止迁移写入并保留原记录，交由该数据库的恢复负责人处理。即使受影响记录已不存在，也应记录依据，而不是把未检查当作不受影响。

`InspectStatus` 是恢复后的只读验证入口，不为记录重新背书。它报错时仍须调查原因，不能以 `Status`、`Apply` 或 `ResolveDirty` 尝试“修复”摘要。真实 SQLite 回归证明框架会拒绝歧义旧记录并保留历史及受保护数据；它没有恢复任何业务数据库，不能代替上表中的数据库证据。

## 验证边界

普通回归包括固定编码向量、旧值兼容、重复方向标记、无效输入、原始字节、快照、取消、错误身份、并发构造及五条 Runner 路径的拒绝。模糊测试验证把 `down` 从 Down 移到 Up 后摘要必须变化。小规模穷举只是有界回归，不是 SHA-256 无碰撞的证明。

CGO 测试通过真实 SQLite 的 `DatabaseStore` 写入历史和 journal，验证旧写入者到新读取者、不同方向定义、独立 dirty journal 恢复校验、拒绝后受保护行和历史/journal 不变，以及普通迁移升级后正常回滚。测试不会向 SQLite 执行无效的独立 `down` 语句，不冒充 SQL Server 存储过程或完整供应链攻击验证。
