# 内置命令

`cmd/think` 注册以下开发宿主命令：

| 命令 | 参数/选项 | 多应用语义 |
|---|---|---|
| `help` / `list` | `help [command]`、`list [namespace]`、`--raw` | 项目级帮助；支持 `-h/--help` |
| `version` | 无 | 输出框架版本 |
| `run` | `--host`、`--port`、`--root` | 启动全部编译期应用 |
| `create` | `<项目名称>` | 在当前目录的空子目录创建完整项目 |
| `build` | `[GOOS/GOARCH]`、`--goarm` | 编译并生成 `dist/<平台>` 发布包 |
| `make:app` | 可选 `<app>` | 创建应用目录并刷新清单 |
| `route:list` | `--app`、排序与详情选项 | 默认应用或显式目标 |
| `config:dump` | 可选 `<name>`、`--app` | 从目标应用配置容器读取并脱敏 |
| `clear` | 可选应用及缓存/日志选项 | 只清理受管路径 |
| `make:*` | `<name>`、`--app` | 写入 `app/<name>`；也支持 `app@Type` |
| `optimize` | 无 | 处理全部编译期应用 |
| `optimize:config` | 可选应用目录 | 构建项目或应用配置快照 |
| `optimize:route` | 可选应用目录 | 构建 URL 生成使用的命名路由缓存 |
| `optimize:schema` | 可选应用目录、`--connection`、`--table` | 查询数据库并缓存真实表字段；`--table=*` 枚举全部表 |
| `route:export` | 可选应用目录 | 校验并导出真实路由清单 |
| `schema:validate` | 可选应用目录/连接/表 | 校验模型映射；指定表时验证可查询性 |
| `service:discover` | 无 | 刷新根清单及每个应用清单 |
| `openapi:generate` | `--check` | 为当前模块生成源码注释元数据，或只读检查产物是否过期 |
| `vendor:publish` | `--force` | 发布扩展资源 |
| `migrate` | `--app` | 操作默认或显式应用迁移 |
| `migrate:status` | `--app` | 展示目标应用迁移状态 |
| `migrate:rollback` | `--app`、`--batches` | 回滚目标应用迁移 |
| `deploy:check` | `--app`、`--strict` | 默认审计全部应用 |

```bash
go run ./cmd/think route:list --app admin
go run ./cmd/think config:dump app.server --app admin
go run ./cmd/think deploy:check --strict
```

`route:list` 会执行目标应用的正式路由加载器后冻结快照，不能把尚未收到首次请求的路由误报为空。`config:dump` 递归隐藏密码、令牌、密钥、授权头、连接串和 URL 等敏感字段。

`deploy:check` 在未指定 `--app` 时按稳定顺序审计全部编译期应用；任一应用失败，或严格模式下出现警告，命令均返回阻断错误。检查包括生命周期、生产配置、数据库策略与连通性、运行目录、Host、运维端点、安全响应头、TLS、迁移、遥测和路由快照。二进制部署无需携带源码发布资料；源码发布流程可显式选择 `deploy.NewReleaseMetadataCheck()`。

## 发布构建

```bash
thinkgo build
thinkgo build linux/amd64
thinkgo build linux/arm --goarm 7
thinkgo build windows/amd64
```

不指定平台时使用当前平台。支持 Linux amd64/arm64/arm（ARM 5、6、7）、Windows amd64/arm64、macOS amd64/arm64。`build.sh GOOS/GOARCH` 与 `build.bat GOOS GOARCH [GOARM]` 兼容原入口，并委托 CLI 构建。

输出目录例如 `dist/linux-amd64`、`dist/linux-armv7`、`dist/windows-amd64`，包含 `thinkgo-nocgo`（Windows 为 `.exe`）、项目和应用的配置 JSON、公共和应用语言 JSON、`public/`、应用模板。配置指定的项目内静态目录、模板目录、异常模板也会按原相对路径复制；不复制 `.env`、运行数据或业务源码。运行时通过环境变量指向的额外文件需由部署环境提供，项目外资源路径会阻止打包。

同平台构建成功后整体替换旧目录，清理过期文件；失败保留上一份成功产物；其他平台目录不变。二进制固定为无 CGO 构建，不包含 SQLite CGO 驱动能力。`build` 不读取应用生成清单，也不生成应用骨架。

Linux 产物还包含 `Dockerfile`、`docker-compose.yml` 和 `.dockerignore`，在产物目录执行 `docker compose up -d --build` 即可部署。Compose 固定匹配构建目标架构，默认暴露宿主 8000 端口（通过 `APP_PORT` 修改），挂载配置目录与持久化运行目录。证书构建阶段使用 Alpine，运行镜像使用 scratch 和非 root 用户。部署外部数据库、密钥或 TLS 时按项目需要补充环境变量、挂载或 Compose 配置。Windows/macOS 产物不生成 Docker 文件。

## 优化缓存

`optimize` 依次执行配置、命名路由和数据库结构优化。`optimize:route` 写入各应用 `runtime/<应用>/route_names.json`，后续应用加载时用于按名称生成 URL；请求处理器和中间件仍来自编译程序。`optimize:schema` 默认读取已注册模型的配置钩子和表前缀；可用 `--connection` 指定连接、`--table` 指定真实表名或 `*` 枚举表。

结构产物写入对应应用的 `runtime/<应用>/schema/<连接>.json`。在连接配置中启用 `fields_cache: true` 后，新进程加载与连接身份匹配的缓存，并用于字段查询；无模型时不要求数据库。改变表结构后应重新生成缓存。损坏或不匹配的缓存会回退正常查询。运行目录不随 `build` 打包，需在目标环境单独生成或提供经过核对的优化缓存。
