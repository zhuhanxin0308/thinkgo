# 字段关系与条件规则

本章包括字段引用、固定日期边界和条件规则。字段比较使用 `reflect.DeepEqual` 时类型也必须一致；日期规则的目标类型由可信规则配置确定，不由请求中是否存在同名字段决定。

## confirm

```text
confirm
confirm:password_confirmation
```

无参数时目标字段默认为当前字段名加 `_confirm`；有参数时使用指定字段。目标字段必须存在，当前值与目标值必须同时满足值和类型一致。

## different

```text
different:old_password
```

当前字段存在时，目标字段也必须存在，且两个值不能 `DeepEqual`。目标缺失会失败；当前字段缺失时，普通非必填规则不会被执行。

## dateFormat

```text
dateFormat:2006-01-02
dateFormat:2006/01/02 15:04
```

参数是 Go `time.Parse` 使用的 layout，不是 PHP 风格日期格式。整个值必须按该 layout 成功解析，参数不能为空。

## 固定日期与日期字段

固定业务边界使用 `beforeDate`、`afterDate`；比较两个字段使用 `beforeField`、`afterField`：

```go
rules := map[string]string{
	"booking_date": "required|date|beforeDate:2026-01-01",
	"started_at":   "required|date",
	"finished_at":  "required|date|afterField:started_at",
}
```

| 规则 | 比较目标 | 当前字段存在时的通过条件 |
|---|---|---|
| `beforeDate:日期` | 规则中的固定日期 | 当前值严格早于固定日期 |
| `afterDate:日期` | 规则中的固定日期 | 当前值严格晚于固定日期 |
| `beforeField:字段名` | 当前数据 map 中的指定字段 | 当前值严格早于目标字段值 |
| `afterField:字段名` | 当前数据 map 中的指定字段 | 当前值严格晚于目标字段值 |

`Date` 规则的参数必须是有效日期，否则在验证计划编译阶段返回 `ErrInvalidRule`，即使当前请求没有该字段也会失败。请求中的同名键不会替换固定日期，也不会影响其有效性。

`Field` 规则按完整键名读取同一数据 map，不解释点路径或字段别名。目标字段缺失、为 `nil`、不是可转换的标量或不是有效日期时，结果为数据违规，不会回退为日期常量。例如 `beforeField:2026-01-01` 明确引用名为 `2026-01-01` 的字段。

当前值和目标值都按以下格式解析：

```text
2006-01-02 15:04:05
2006-01-02
RFC3339Nano
```

不带偏移的日期时间按本次验证的应用时区解析，遵循 `WithLocation` 或验证器的 `SetLocation`；带偏移的 RFC3339 值使用自身偏移。共享编译计划只保存目标类型，不冻结某次调用的时区。

所有日期比较都不包含相等情况。当前字段缺失时，与其它普通规则一样跳过；需要强制存在时组合 `required`。

## after 与 before 的兼容语法

```text
after:2024-01-01
before:start_at
```

`after`、`before` 保留简写，但在编译规则时按照上述支持的日期格式确定含义：

- 参数能解析为有效日期时，始终是固定日期，不读取请求中的同名字段。
- 其它非空参数始终是字段名，目标缺失或日期值无效时失败，不在运行时切换含义。

例如 `before:2026-01-01` 是固定截止日期；`before:start_at` 是字段引用。为保留普通字段名兼容性，`before:2026-02-30` 也会被视为字段引用。新代码应使用 `beforeDate`、`afterDate` 表达固定边界，使日期拼写错误立即成为配置错误。

### 从旧的字段优先语义迁移

旧版本在请求存在同名键时优先读取字段。现在合法日期参数优先且固定为日期常量，因此额外请求键不能改写应用指定的截止日期。

确实使用合法日期文本作为字段名的调用者，需要将 `before:2026-01-01` 改为 `beforeField:2026-01-01`，`after` 同理。普通的 `before:deadline`、`after:start_at` 字段引用保持原有行为。

四个显式规则是新增语法；旧框架会返回 `ErrUnknownRule`。应先升级使用该规则的框架实例，再启用共享规则配置中的新名称。规则参数的引号仅用于语法转义，不用于选择日期或字段类型。

日期目标隔离不等于拒绝所有未知请求字段。完整请求 map 仍可使用 `DisallowUnknownFields()` 或应用字段白名单控制额外输入；字段之间的比较也不替代业务授权。

## requireIf

```text
requireIf:account_type,company
```

当关联字段存在、能转换为标量文本且等于期望值时，当前字段必须存在且非空。关联字段缺失、不是可比较标量或值不相等时，条件不触发，规则通过。

## requireWith

```text
requireWith:email,phone
```

当参数列表中任意一个关联字段存在且非空时，当前字段必须存在且非空。所有关联字段都缺失或为空时，规则不触发。

## 与普通可选规则的区别

验证器对缺失字段会跳过普通规则，但 `required`、`requireIf` 和 `requireWith` 被标记为需要检查字段存在性。因此条件规则可以单独用于不存在的字段：

```go
"company": "requireIf:type,staff",
"phone":   "requireWith:email",
```
