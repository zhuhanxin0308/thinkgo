# ThinkGo 开发规范

本规范是 ThinkGo 框架与基于它开发的业务代码的**强制约束**。README 偏重「怎么用」，本文档偏重「必须怎么做、不能怎么做」。两者冲突时以本文档为准。

适用范围：`framework/` 框架核心、`app/` 业务代码、`route/`、`config/`、`cmd/`、测试代码。

---

## 1. 总则

1. **正确性优先于便利**。不允许通过放宽类型检查、跳过错误处理、降低测试质量来「让它先跑起来」。
2. **请求级状态绝不写入全局**。框架是长期运行的多协程进程，任何包级变量、单例字段都可能被并发读写。
3. **安全默认**。新增能力的默认配置必须是安全的（如自动路由默认关闭、删除/更新必须带 WHERE），需要时再由使用者显式放开。
4. **复用框架既有能力**：容器、配置、日志、事件、缓存、中间件、验证器。不要另起炉灶。
5. **改动可解释、可测试、可回滚**。每个非平凡改动都要有对应测试，且能说清为什么这么改。
6. 提交前必须通过：`go build ./...`、`go vet ./framework/...`、`go test ./...`。

---

## 2. 目录与分层

```
app/          业务代码（controller / middleware / model / validate / lang）
route/        路由定义（通过 RegisterRouteLoader 注册）
config/       JSON 配置，文件名即一级命名空间
cmd/          命令行入口
framework/    框架核心（除修复框架能力外，禁止写入业务逻辑）
public/       静态资源
runtime/      运行时产物（日志/缓存/会话/证书），不入库
docs/         文档
```

- 业务逻辑**只能**放在 `app`、`route`、`config`、`cmd`。
- 框架核心改动需谨慎，必须配套测试，且不得引入对具体业务的依赖。
- 分层依赖方向单向：`app` 依赖 `framework`，`framework` 不依赖 `app`。框架内部用接口（如 `db.Logger`、`exception.AppContract`）解耦，避免循环依赖。

---

## 3. 命名规范

- 文件名：控制器、路由、中间件、验证器、模型一律小写蛇形（`user_profile.go`）。
- 导出标识符 `PascalCase`，非导出 `camelCase`。
- 控制器注册名必须与路由中引用名一致（`RegisterController("User", ...)` ↔ `"User@Index"`）。
- 数据库表/字段名用小写蛇形；结构体字段用 `thinkgo:"col_name"` 标签映射。
- 常量集中定义，避免散落的魔法值（参考 `framework/constants.go`、各包 `constants.go`）。

---

## 4. 注释与文档

- **代码注释统一使用中文**，解释「为什么」而非复述「做了什么」。
- 每个导出类型、函数、方法必须有文档注释，首词为标识符本身。
- 对应 ThinkPHP 的能力，注释中标注对应关系，便于迁移者理解。
- 安全相关、并发相关的非显然决策必须写明意图（例如「在写锁内二次检查缓存，保证单例只构建一次」）。
- 新增/调整公共能力时，同步更新 [README.md](../README.md) 与本规范。

---

## 5. 错误处理

1. **禁止吞错**。返回 `error` 的调用必须处理：要么向上返回，要么记录日志，要么有明确注释说明为何可忽略。
2. 数据库、文件、网络等 IO 的写操作必须显式处理错误。
3. 行集迭代必须检查 `rows.Err()`，不能因迭代中断而静默返回不完整结果。
   ```go
   for rows.Next() { /* ... */ }
   if err := rows.Err(); err != nil { return nil, err }
   ```
4. 不要对外暴露内部错误细节。生产环境（非 debug）只返回通用信息；详细堆栈与上下文写入日志。异常堆栈页仅在 `debug && 回环地址` 下暴露。
5. 业务错误返回结构化响应（`code`/`msg`/`data`），用 `BusinessException`/`Controller.Error` 等统一出口。
6. `panic` 只用于不可恢复的编程错误；请求处理链中的 panic 由 Recovery 中间件统一兜底，不要依赖 panic 做正常流程控制。

---

## 6. 并发与状态

框架是常驻多协程进程，这一节是**事故高发区**，必须严格遵守。

1. **请求级对象不得共享**：`*context.Request`、`*context.Response`、控制器实例、请求级 Session/Cookie 都是每请求新建。控制器通过容器工厂模式（`BindFactory`）每次请求 `reflect.New` 出新实例。
2. **不要把请求数据写入包级变量或单例字段**。需要跨中间件传递时用 `req.Set()` / `req.GetData()`（内部有读写锁保护）。
3. **共享可变状态必须加锁**，并保证锁粒度与顺序一致：
   - 单例/容器缓存用双重检查锁，避免「并发重复构建 + 后写覆盖」破坏单例语义。
   - map 的并发读写必须用 `sync.RWMutex` 或 `sync.Map` 保护（如缓存 store 注册表、配置查询缓存、验证器正则缓存）。
4. **持锁期间避免回调用户代码或递归解析**，防止死锁。
5. **map 遍历顺序不确定**：依赖顺序的场景（如校验错误「第一条」、批量字段顺序）必须显式排序。
6. 后台协程（会话回收等）必须提供可停止的退出机制，并在进程退出时关闭。

## 7. 安全规范

### 7.1 SQL 与标识符

- **值一律参数化**（`?` 占位符），由方言层 `Rebind` 转换；**绝不**把用户输入拼进 SQL 字面量。
- **标识符（表名、字段名、操作符、排序）一律走白名单校验**：`validateIdentifier`、`validateIdentifierList`、`validateOrderClause`、`validateOperator`、`validateJoinCondition`。新增任何拼接标识符的入口，都必须先过这些校验。
- 优先使用参数化 API：`WhereField` / `WhereMap` / `WhereIn` / `WhereBetween` / `WhereLike` / `WhereNull`。
- `WhereRaw` / `HavingRaw` / `DB.Query` / `DB.Execute` 是**显式逃生舱**，不做标识符校验，调用方必须自行保证参数化与输入安全，且应在代码评审中重点审查。
- `Update` / `Delete` / `ForceDelete` 禁止无 WHERE 执行（框架已强制），不要绕过。

### 7.2 路径穿越

- 任何把外部输入拼成文件路径的地方（视图模板名、下载文件、静态资源），必须做 `..`/绝对路径净化并校验落在允许的根目录内（参考 `resolveStaticFilePath`、视图驱动 `safeTemplatePath`、`Response` 的 `resolveWithinBase`）。
- `Response.Download(path, filename)` 的 `path` 必须是受信任路径；`filename` 已由框架净化（取末段、去引号与换行）以防 `Content-Disposition` 头注入。
- **下载路径可能来自用户输入时，必须使用 `Response.DownloadSafe(baseDir, relativePath, filename)`**：它会拒绝绝对路径与 `..` 逃逸，确保最终文件落在 `baseDir` 内，越界返回 403。禁止把未校验的用户输入直接传给 `Download`。

### 7.3 输出与注入

- HTML 输出统一用 `html/template`（自动转义）；调试条等服务端拼接 HTML 必须对所有动态片段 `html.EscapeString`。
- JSONP 回调名必须白名单校验后才输出（框架已实现，不要绕过）。
- 重定向 `Location` 不要直接回显未校验的用户输入，防开放重定向。

### 7.4 鉴权、代理与会话

- 客户端 IP / 协议只在请求来自**可信代理网段**时才信任 `X-Forwarded-For` / `X-Forwarded-Proto`；可信网段通过 `trusted_proxies` / `SERVER_TRUSTED_PROXIES` 配置，默认空（不信任）。
- 登录、提权等敏感操作后必须 `Session.Regenerate()` 防会话固定。会话 ID 仅复用后端已知且字符集合法的标识。
- 静态文件在中间件之前处理，**不会经过鉴权/CORS 中间件**；需要保护的资源不要放在 `public/`。
- 自动路由会暴露控制器全部导出方法，默认关闭；开启时不要在控制器放不希望被路由的导出辅助方法。

### 7.5 密钥与敏感信息

- 密钥、密码、证书私钥**禁止入库**：`.env`、`runtime/` 已在 `.gitignore` 中，编译产物（`*.exe`、二进制）同样不入库。
- 生产环境禁止 `APP_DEBUG=true` / `APP_TRACE=true`；Cookie/Session 在 HTTPS 下应置 `secure=true`，并配置 Cookie `secret` 以启用签名。
- 日志/异常页对 `password`、`token`、`authorization`、`cookie` 等敏感字段必须脱敏（框架已实现，扩展时沿用 `isSensitiveKey`）。

## 8. 数据库与 ORM 规范

- 每次链式查询是独立 `Query` 实例，不跨请求复用状态；需要复用基础条件时用 `clone()`。终端方法（`Find`/`Count`/`Select` 等）在克隆上执行，不污染原查询。
- 写操作处理错误并检查受影响行数。批量插入要求各行字段集合一致；`InsertAll` 超过占位符上限会自动分批并包裹事务保证原子性。
- 表前缀由配置统一追加：`Name()` 加前缀，`Table()` 用完整表名；JOIN 表跟随主表的前缀规则。
- 自动时间戳、软删除、获取器/修改器/搜索器走 Model 层统一能力，不要在业务层手搓。
- 事务优先用 `DB.Transaction(fn)` / `DB.TransactionContext(ctx, fn)` 闭包形式，自动 Commit/Rollback；panic 会回滚并重新抛出。
- HTTP 请求内的查询/事务应通过 `WithContext` / `TransactionContext` 传入请求 context，使慢查询随请求取消，避免拖垮连接池。
- 分页大偏移量（OFFSET）性能差且并发增删会漏/重，海量数据遍历用 `ChunkById`（主键游标）。
- `Count`/`Paginate` 对 JOIN/GROUP/DISTINCT 会自动包子查询统计真实 total，无需手写。
- 跨方言：SQL 统一 `?` 占位符由 builder 转换；PostgreSQL 自增主键依赖 `INSERT … RETURNING id`（主键列需为 `id`）。
- 数据库错误日志只记字段名与参数数量，禁止把字段值/绑定参数写入日志。

## 9. 配置规范

- 配置文件 `config/*.json`，文件名即一级命名空间。
- **读取用类型安全访问器** `GetBool` / `GetInt` / `GetString` / `GetMap`，缺失或类型不符时回退默认值；**禁止**对裸 `Get` 的返回值直接做类型断言（`.(bool)`、`.(map[...])`），那会在配置异常时让进程启动即 panic。
- **`Get` / `GetMap` 返回的是内部配置引用（零拷贝），契约为只读**：禁止直接修改返回的 map/slice，否则会污染共享配置并与并发读者竞争。确需可变副本时用 `GetMapCopy`（深拷贝，按需付出拷贝代价）。
- **所有配置写入只能经由 `Set`**（持写锁、失效查询缓存）。覆盖嵌套配置用点路径，如 `Set("app.server.tls.enable", true)`，`Set` 会自动创建缺失的中间子树——不要用「`Get` 取出 map → 原地改 → 再 `Set`」的模式去修改共享引用。
- 优先级：`.env`/环境变量 > `config/*.json` > 框架默认值。
- 新增配置项必须有合理默认值与回退逻辑，非法值不得导致启动崩溃。
- `.env` 仅写入框架内部存储，不调用 `os.Setenv`，避免敏感值泄漏到子进程环境。

---

## 10. 缓存规范

- 驱动语义统一：`file`/`redis` 均 JSON 序列化任意值，反序列化后数值为 `float64`，业务读取时注意类型。
- Redis store 必须配置 `prefix`，使 `Flush()` 按前缀清理；不配 `prefix` 时 `Flush()` 会 `FLUSHDB`（影响整个 DB 索引），仅在独占 DB 时可接受。
- 所有 Redis 操作带超时（`timeout_ms`），避免后端抖动拖垮请求协程。
- `Inc`/`Dec` 在 Redis 上原子；文件驱动通过进程内锁保证单机原子，跨进程计数请用分布式锁（`Cache.Lock`）。
- 标签缓存的成员维护非跨进程原子，分布式场景谨慎使用。

---

## 11. 日志规范

- 统一用 `app.Log`，按级别记录；带上下文用 `*Ctx` 方法传 `map[string]interface{}`。
- 不同类别日志用命名通道（`app.Log.Channel("sql")`）隔离。
- 日志异步批量刷盘，进程退出前必须 `Shutdown()`（`app.Run()` 已处理）。
- 不要在热路径打印大对象；敏感字段先脱敏。

---

## 12. HTTP / 中间件 / 控制器规范

- 中间件签名固定：`func(*context.Request, func(*context.Request) *context.Response) *context.Response`，必须调用 `next(req)` 或显式短路返回。
- 中间件拿到下游响应后要判空再设置头部（下游可能返回 nil）。
- 执行顺序：全局 → 路由 → 控制器中间件 → 控制器动作；终结逻辑用 `Lifecycle`/`PipeLifecycle`。
- 控制器每请求新建，禁止字段缓存请求级状态；返回 `string`/`*Response`/任意可 JSON 化对象。
- 控制器内通过 `c.App`、`c.Request` 访问框架能力，不要访问包级单例。

---

## 13. 测试规范

- 新功能、修复、重构**先写有意义的测试**，验证行为而非堆覆盖率。
- 修 bug 时先写能复现的失败用例，再修。（本项目的 JOIN 带空格条件 bug 即由新增测试暴露。）
- 涉及文件/缓存/数据库/会话等 IO 的测试必须用临时目录并清理（`t.TempDir()`、`t.Cleanup`）。
- 框架核心测试放对应 `framework` 子包；应用集成测试可放项目根，验证注册链路与真实 HTTP 行为。
- 安全相关能力必须有「拒绝恶意输入」的负向测试（参考 `query_security_test.go`）。
- 提交前 `go test ./...` 全绿；并发敏感代码尽量用 `go test -race`（需 CGO）。

---

## 14. 依赖管理规范

- 统一 Go Modules，不提交 `vendor/`；新增依赖后 `go mod tidy`。
- 升级：`go get -u ./...` 升到同主版本内最新，随后 `go mod tidy && go build ./... && go test ./...`。
- 跨大版本（`/v2`、`/v3`）升级是破坏性变更，单独评估并改造代码与测试，不在常规升级中顺带。
- 优先选择**维护中**的依赖，避免已废弃/归档库（如 SQL Server 驱动用 `microsoft/go-mssqldb` 而非已废弃的 `denisenkom/go-mssqldb`）。
- 注意 retracted（撤回）版本，及时升级到修复版。
- 依赖抬高 `go` 指令最低版本时，确认团队工具链可用（`GOTOOLCHAIN=auto` 会自动拉取），或权衡后锁定不抬高版本的依赖。
- 提交前 `go mod verify` 校验完整性。国内代理：`GOPROXY=https://goproxy.cn,https://goproxy.io`。

---

## 15. 提交与评审

- 一次提交聚焦一件事，信息说清「做了什么、为什么」。
- **禁止批量脚本式无差别改代码**，改动逐文件进行、可解释。
- 禁止提交编译产物、运行时文件、密钥。
- 评审重点：错误处理是否完整、是否引入共享可变状态、是否有未参数化的 SQL/未校验的标识符、是否绕过安全默认、是否有对应测试。

---

## 16. 性能注意事项

- 启动期一次性解析配置，热路径避免重复类型转换与配置树遍历（参考 HTTP 内核 `parseConfig`）。
- 路由：静态路由走 map O(1)；动态路由请求路径只切分一次、路由片段注册期预切分。可重复编译的正则要缓存。
- 避免对大响应体做整体复制/小写化（Trace 仅对 HTML 响应处理）。
- 文件句柄、连接等资源要复用并在合适时机释放，避免随时间泄漏。
- 数据库连接池参数（最大连接数、生命周期）按部署环境配置，不硬编码。

---

> 任何对本规范的例外都必须在代码评审中显式说明理由并获得确认。规范随框架演进持续更新。
