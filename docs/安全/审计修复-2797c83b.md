# 2797c83b 审计问题修复说明

本变更针对本轮确认的限流、Redis 清理、CSRF 提交、HTTP deflate 和文件 URL 问题，不代表已经完成整个框架的安全验收。

## 限流策略键与部署迁移

`middleware.RateLimit` 使用 `ratelimit.PolicyKey` 将原始键与 Rate、Period、Burst 绑定；多个中间件共用同一 Store 时，不同策略不再触及同一额度状态，相同策略与相同原始键仍跨实例共享额度。需要隔离相同参数的不同业务时，继续在 Key 中加入稳定业务标识，例如 `login:<account>`。

PolicyKey 先校验原始长度与非法字符，再规范化并摘要；摘要不能成为绕过 Store 输入上限的入口。底层 Store.Take 的原始键接口没有改变；直接使用 Store 的代码也必须保证一个键只对应一个策略，或显式调用 PolicyKey。重置中间件额度时，用 `PolicyKey(rawKey, limit)` 的结果调用相应 Store.Reset。

新旧中间件物理键格式不同。部署应协调切换全部实例，不能声称混合版本共享同一额度；旧 Redis 键会按原 TTL 过期。修改策略参数也会进入新的额度空间。严格要求跨版本连续额度的部署，应由外层网关在切换期间保持统一限流，或在维护窗口完成切换，不要删除活动状态作为迁移步骤。

## Redis 清理边界

Clear、ClearPrefix 和 ClearPrefixIfContext 共用键归属检查。已知驱动前缀、显式清理前缀下的保留锁和 fencing 元数据不删除；扫描到其他位置的保留标记时无法区分业务名称与外部命名空间，因此返回 `ErrAmbiguousRedisClearScope`（同时匹配 `ErrUnsafeRedisFlush`），不把不完整清理报告为成功。

这是一项失败关闭的兼容性收紧：空前缀显式授权或祖先前缀不再允许误删其他命名空间锁。应使用明确的业务命名空间或隔离 Redis DB；条件清理可以通过 match 排除不归属本业务的键。保留标记碰巧出现在业务键内时也会报告歧义，需迁移该命名或明确排除，不能使用模糊匹配后静默遗留数据。

清理是逐批 SCAN，不是全库事务。后续批次报错时，之前已经删除的数据不会回滚。锁键布局、owner 及续租/解锁协议没有改变；本修复不对显式 Delete/Reset 等调用提供额外保护。

## CSRF 响应边界

安全方法缺少有效 Token 时，在执行下游前生成 Cookie 并优先注册 BeforeCommit 钩子，覆盖标准 Handler 的 WriteHeader、Write 和 Flush。独立标准 writer 在下游前设置头；未提交的内存响应也保留 Cookie，提交钩子负责去重。Token 校验、来源校验及重复 Cookie 拒绝逻辑不变。

## HTTP deflate

Content-Encoding: deflate 按 RFC 9110 §8.4.1.2 使用 zlib 封装，不再输出裸 DEFLATE。往返测试使用独立 zlib 解码器，并保留压缩级别、Flush 和池化 Reset 回归测试。此协议纠正不保留非标准裸流模式。

## 文件 URL

Local.URL 接受原始逻辑文件名，按路径段转义保留字符，并保留配置 URL 的有效路径转义、查询与片段。已有调用方不要预先 PathEscape 文件名；字面量 `%2F` 文件名正确编码为 `%252F`。普通文件名及目录分隔符保持原语义，文件读写与根目录约束不变。
