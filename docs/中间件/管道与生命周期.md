# 管道与生命周期

`framework/middleware.Pipeline` 负责组合同一作用域内的中间件。全局、路由和控制器管道都使用同一个 `Handler` 约定，但路由和控制器管道的终结回调最终仍会写入当前请求，由 HTTP 内核统一执行。

## 基础 API

```go
pipeline := middleware.NewPipeline()
pipeline.Pipe(first)
pipeline.Unshift(earliest)
response := pipeline.Then(request, destination)
```

API 行为如下：

| API | 行为 |
|---|---|
| `NewPipeline` | 创建空管道和空别名表 |
| `Pipe` | 追加普通中间件 |
| `Unshift` | 插入管道头部，最先执行 |
| `Then` | 按管道顺序执行并返回响应 |
| `ThenWithTerminators` | 执行管道，同时返回本次新增的终结回调 |

管道会从尾部向前构造闭包，因此 `Pipe(first); Pipe(second)` 的处理顺序是 `first -> second -> destination`。`destination` 应该是非空函数；管道 API 不会替调用方检查所有自定义函数的契约。首个中间件现在直接调用，反向链只为后续节点构造闭包；控制器等动态处理函数切片可通过 `ThenHandlers` 直接执行，避免重复创建 `Pipeline`。

路由注册时会装配只读的中间件管道，冻结后的请求只复用该管道，不再复制路由中间件切片或重复注册处理函数。调用 `Route.Middlewares()` 仍然返回副本，现有外部修改隔离语义保持不变；路由在注册前调用 `WithoutMiddleware` 会同步刷新内部管道。

## 别名与优先级

```go
pipeline.Alias("auth", Auth)
pipeline.PipeByName("auth")
pipeline.SetPriority([]string{"csrf", "auth"})
```

`Alias` 注册别名，`ResolveAlias` 查询别名，`PipeByName` 按别名追加中间件。`PipeByName` 找不到别名时会静默忽略，因此依赖保护中间件的代码应先用 `ResolveAlias` 检查，或在启动测试中验证管道快照。

`SetPriority` 只影响通过 `PipeByName` 注册且带有别名的条目：优先级列表中的条目稳定地排在未指定条目前面，列表内部按给定顺序排列，未指定条目保持原相对顺序。通过 `Pipe` 或 `Unshift` 注册的匿名条目没有别名，不参与名称排序。

旧的 `PipeByName` 保持兼容行为：别名不存在时静默忽略。安全敏感的装配应使用严格入口：

```go
if err := pipeline.PipeByNameStrict("csrf"); err != nil {
	return err
}
```

`PipeByNameStrict` 在别名为空、别名未注册或处理函数为空时返回稳定的 `ErrMiddlewareAliasNotFound`，已注册别名的优先级和执行顺序不变。框架自身对必须存在的 CSRF 别名使用严格入口，业务迁移旧代码不需要改变原 API。

别名和优先级是进程内 API。当前 `config/middleware.json` 中的 `alias`、`priority` 不会被 `App.initialize` 自动读取并写入管道。

## terminate 生命周期

```go
handler := func(request *context.Request, next func(*context.Request) *context.Response) *context.Response {
    return next(request)
}

terminator := func(request *context.Request, response *context.Response) {
    // 在响应发送完成后记录收尾信息。
}

pipeline.PipeLifecycle(handler, terminator)
```

也可以直接使用 `middleware.Lifecycle(handler, terminator)` 得到普通 `Handler`。非空的 handle 开始执行时，终结回调才会追加到请求上下文；因此短路时只会收集真实执行过的中间件。

HTTP 内核在响应发送后调用 `RequestTerminators`，并按 handle 进入顺序执行回调。terminate 不是逆序执行；需要逆序释放资源时应在单个中间件中显式组织顺序。终结回调发生 panic 时由 HTTP 内核记录日志并继续执行后续回调，不修改已经发送的响应。

`RequestTerminators` 返回内部切片的副本。跨全局、路由和控制器管道嵌套执行时，`ThenWithTerminators` 只返回本次新增部分，避免重复执行外层已经收集的回调。
