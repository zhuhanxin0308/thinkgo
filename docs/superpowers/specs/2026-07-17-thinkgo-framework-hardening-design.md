## 1. 目标与约束

本次修复覆盖统一 HTTP 宿主、应用生命周期、Windows 文件 Session、请求 Trace、访问日志、语言检测、动态路由、中间件别名和性能基准。目标是在不破坏现有公开 API、默认配置和兼容行为的前提下，消除已确认的安全与并发问题，并降低框架热路径开销。

全局约束如下：

- 框架在没有数据库配置、数据库驱动未注册或数据库连接失败时仍能启动，非数据库模块必须可正常使用。
- 不引入分布式锁；缓存标签继续维持当前单进程一致性语义。
- 不修改 PostgreSQL、Cookie、Session、路由和日志的现有默认配置值。
- 不更改现有 HTTP 状态码、路由优先级、方法协商和公开方法签名。
- 所有新增选项保持兼容默认值，未显式启用时行为与当前版本一致。
- 生产代码注释使用中文；禁止魔数和无界运行时集合。
- 所有修复先写稳定失败测试，再实现，再运行包级与全量回归。

## 2. MultiHttp 请求体所有权

`MultiHttp` 只克隆请求元数据和 URL，不读取、复制或恢复请求体。克隆请求直接持有原请求的单次消费 Body，并交给唯一目标应用处理。

请求体大小限制仍由目标应用的 Context 层执行，未知 Content-Length 的分块或流式请求超过限制时必须返回 413。移除“宿主处理后原始请求体仍可重新读取”的内部测试假设，因为 `net/http.Handler` 不保证该行为，且为满足该假设进行无界 `io.ReadAll` 会绕过限制并导致内存拒绝服务。

路径改写仅发生在克隆请求的 `URL.Path`、`URL.RawPath` 和 `RequestURI`，原请求的 URL、Header、Host、TLS、RemoteAddr 等元数据保持不变。

## 3. 多应用生命周期

`ApplicationManager` 是全部 App 生命周期的唯一所有者。`MultiHttp.Run` 在冻结路由并校验宿主后，通过 `manager.Run(hostKernel)` 启动宿主，不再直接组合 `Boot`、运行宿主和 `Close`。

管理器必须拒绝在 booting 或 running 状态下执行外部 `Close`，避免宿主仍在处理请求时释放 App 资源。启动失败继续在监听前回滚；宿主退出后按应用注册逆序关闭，并使用 `errors.Join` 保留宿主和关闭错误。

`MultiHttp` 自身仍阻止重复 `Run`。路由冻结失败和宿主不可用发生在进入管理器运行态之前，必须安全关闭应用且保留原错误。

## 4. Windows 文件 Session 锁

Unix 路径保持现有快速实现。Windows 使用平台专用文件打开函数创建和读取锁文件，句柄共享标志必须允许其他进程读取、写入和删除，避免锁拥有者释放文件时与竞争者打开文件发生 sharing violation。

删除锁文件遇到 Windows 共享冲突时执行有界重试。每次重试前重新读取锁文件身份和 owner，只有仍属于当前锁实例时才能删除，防止误删已经被其他进程重新创建的锁。重试次数和退避时间使用具名常量；非共享冲突立即返回。

## 5. 请求级 Trace

应用级 `Debug` 只保存 Trace 配置，不保存跨请求采集数据。只有通过现有授权检查的本地 Trace 请求才创建请求级收集器；远程请求和关闭 Trace 的普通请求不增加收集器分配。

请求级收集器按日志、SQL、缓存、变量和文件类别设置具名上限，达到上限后记录截断状态，不再继续增长。

Cache 的驱动和生命周期状态继续共享，但调试器从共享 `cacheState` 移到轻量 Cache facade。新增 `Cache.WithDebug(*debug.Debug) *Cache`，返回共享同一状态、只替换请求级调试器的 facade；`Store`、`Tag` 等派生对象继续传递该 facade，不污染应用根缓存服务。

View 新增显式请求级渲染入口，控制器渲染时传入当前请求收集器。不得使用 goroutine-local、包级“当前请求”或其他隐式全局状态。

## 6. 日志与语言检测热路径

日志级别在配置变更时生成不可变原子快照。访问日志在构造消息、字段 map 和格式化字符串之前检查 Info 是否启用；禁用访问日志时不产生这些额外分配。

异步日志队列默认继续使用当前同步回退策略。新增可选 `drop` 溢出策略和原子丢弃计数；只有显式配置后才丢弃，默认行为不变。

语言模块在初始化或 Load 时预计算标准化来源、允许语言集合、Header 前缀和稳定优先顺序。请求检测跳过空来源，并通过只读 map 查找，避免每次请求复制配置、创建错误和排序。公开 `DetectionConfig` 继续返回防御性副本，内部使用不可变快照。

## 7. 动态路由索引

静态路由继续使用现有 map。`Freeze` 为动态路由构建只读分段索引，展开现有上限内的可选参数分支，并保留当前 specificity 和注册顺序。

匹配结果必须与现有线性匹配器完全一致，包括静态段、必选和可选参数、正则约束、域名、ANY、HEAD 回退、自动 OPTIONS、405、路由优先级和注册顺序。线性匹配逻辑在测试中作为语义基准；只有属性测试和模糊测试一致，且 10、100、1000、10000 条动态路由基准没有统计显著回退时才保留新索引。

请求匹配阶段不得获取写锁、重新排序全部路由或为全部候选创建切片。冻结后索引只读，路由注册仍在 Freeze 后被拒绝。

## 8. 兼容与安全策略

现有 `Pipeline.PipeByName` 保留别名不存在时忽略的行为。新增 `PipeByNameStrict`，别名不存在时返回可被 `errors.Is` 判断的稳定错误；新代码和安全敏感配置可显式采用严格接口。

反向代理安全判断统一复用 `trusted_proxies`：只有来源地址匹配可信代理时才接受 `X-Forwarded-Proto` 并据此生成 Secure Cookie。IPv4、IPv6、本机代理和 CIDR 均使用同一匹配器，非可信来源的伪造转发头继续被忽略。

生产环境发现空 Cookie 或 CSRF 密钥、空 `allowed_hosts`、关闭 CSRF 时，只输出一次不包含密钥值的启动安全告警，不阻止启动，不改变开发环境默认配置。

数据库可选启动属于明确兼容行为，不增加强制数据库模式，也不把连接失败升级为宿主启动失败。

## 9. 性能基准与验收

基准工具不再保存每个请求延迟，改为固定内存的高动态范围延迟直方图。若引入第三方实现，使用实施时可验证的最新稳定版本，并仅用于 benchmark 命令。

新增经过 `ApplicationManager + MultiHttp` 的 Go Benchmark 和端到端健康场景。性能比较必须在同环境、同配置、完成预热后重复运行，至少同时比较统一宿主、单应用框架路径和原生 `net/http` 控制路径。

验收覆盖以下场景：

- 未知长度大请求由目标应用返回 413，宿主不进行整包读取或复制。
- 启动中和运行中外部关闭被拒绝，宿主退出后资源只关闭一次。
- Windows 文件 Session 在线程和独立进程竞争下不出现 sharing violation。
- Trace 数据请求间与并发间隔离，达到上限后有明确截断标记。
- 禁用访问日志和 Trace 时不增加热路径堆分配。
- 无数据库配置与数据库不可达时，应用和非数据库模块可正常启动使用。
- 动态路由新旧匹配结果完全一致，并通过规模化命中、未命中基准。
- 整体和本次涉及核心包的有效单元测试覆盖率不低于 80%。
