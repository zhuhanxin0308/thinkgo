# ThinkGo 多应用架构升级设计

## 设计状态

- 日期：2026-07-16
- 状态：已实现并通过当前主线的多应用、无数据库启动、并发隔离和 Race 验证；正式发布仍受许可证、制品签名/溯源和生产容量证据约束。
- 参考实现：上级目录 `thinkphp/vendor/topthink/think-multi-app` 与 `thinkphp/vendor/topthink/framework`

## 1. 背景与当前问题

ThinkPHP 的多应用能力由应用解析、应用目录切换和应用级配置加载共同完成。`think-multi-app` 会根据入口、域名、URL 首段和应用映射确定目标应用，然后切换应用目录、命名空间、路由目录、运行时目录、语言包、中间件和应用配置。

设计基线（2026-07-16）：ThinkGo 当时只有一个 `framework.App`，控制器、路由加载器和全局中间件通过包级注册表接入。该问题已由当前主线的 `ApplicationManager`、应用级注册表和 `MultiHttp` 实现替代；本段保留为升级前的风险记录，不代表当前代码状态。

本次升级将应用目录作为完整边界，使用多个独立的 `framework.App` 运行时，并由一个统一 HTTP 宿主负责请求分发。

## 2. 目标与非目标

### 2.1 目标

- 使用 `app/<应用名>/` 作为每个应用的完整目录边界。
- 在同一进程内运行 `index`、`admin`、`api` 等多个应用。
- 按 ThinkPHP 风格支持默认应用、URL 首段、应用映射、域名绑定和禁止应用列表。
- 为每个应用提供独立的容器、配置、路由、中间件、事件、Provider、数据库、缓存、日志、Session、语言包和运行时目录。
- 保持请求并发安全，应用解析期间不修改其他请求或其他应用的共享状态。
- 让命令行代码生成、路由列表、配置查看和运行服务都能识别目标应用。
- 迁移现有单应用目录并同步全部架构文档引用。

### 2.2 非目标

- 不在运行时扫描并加载未编译的 Go 包。Go 应用必须通过编译期导入完成组件注册。
- 不在同一进程内为不同应用监听不同端口。网络监听属于统一 HTTP 宿主。
- 不保留 `app/controller`、`app/model`、根目录 `route` 等扁平目录兼容层。
- 不允许请求期间修改应用实例的路由、配置、注册表或资源指针。

## 3. 目录结构

升级后的项目结构如下：

```text
thinkgo/
├── app/
│   ├── index/
│   │   ├── application.go
│   │   ├── controller/
│   │   ├── middleware/
│   │   ├── model/
│   │   ├── validate/
│   │   ├── lang/
│   │   ├── route/
│   │   ├── config/
│   │   ├── event.go
│   │   ├── provider.go
│   │   └── common.go
│   └── admin/
│       ├── application.go
│       ├── controller/
│       ├── middleware/
│       ├── model/
│       ├── validate/
│       ├── lang/
│       ├── route/
│       ├── config/
│       ├── event.go
│       ├── provider.go
│       └── common.go
├── config/                 # 全局配置和统一 HTTP 宿主配置
├── runtime/
│   ├── index/
│   └── admin/
├── public/                 # 全局公开静态资源
├── cmd/
├── framework/
└── main.go
```

控制器、中间件、模型、验证器、多语言和路由定义必须放在对应的应用目录下。`event.go`、`provider.go` 和 `common.go` 用于保存应用级事件、服务提供者和公共初始化逻辑。

根目录 `config/` 保存全局配置和统一 HTTP 宿主配置。应用目录下的 `config/` 在全局配置之后加载，用于覆盖应用自己的业务、路由和资源配置。HTTP 监听地址、端口、TLS 和 HTTP/3 等宿主级配置只能由根目录配置决定，应用配置不能改变同一进程的网络监听边界。

根目录 `.env` 是进程级环境配置。应用级运行时文件统一写入 `runtime/<应用名>/`，避免日志、缓存、Session 和其他运行时产物相互覆盖。

## 4. 应用定义与注册

每个应用通过 `application.go` 暴露一个编译期应用定义。应用定义至少包含应用名、应用目录和注册回调：

```go
framework.MustRegisterApplication(framework.ApplicationDefinition{
    Name: "index",
    Path: "app/index",
    Register: func(app *framework.App) error {
        // 注册当前应用的控制器、路由、中间件和 Provider。
        return nil
    },
})
```

应用入口包负责导入本应用的 `controller`、`middleware` 和 `route` 子包，然后在注册回调中调用当前 `App` 的应用级注册方法：

- `RegisterController`：注册控制器类型，控制器实例仍由容器工厂按请求创建。
- `RegisterRouteLoader`：注册当前应用的路由加载器。
- `RegisterGlobalMiddleware`：注册当前应用的全局中间件。
- `RegisterProvider`：注册当前应用的 Provider。
- `Event.Listen`：注册当前应用的事件监听器。

应用代码不再通过包级全局注册表注册控制器、路由和中间件。现有包级注册 API 如果保留，只能作为单应用调用方的弃用适配路径，不参与多应用宿主的应用注册和隔离。

模型和验证器是普通 Go 包，不需要加入框架注册表；控制器通过应用注册回调引用它们，保持 `Controller -> Validator -> Service -> Model/ORM` 的业务调用边界。

由于 Go 不支持运行时加载新的 Go 包，新增应用必须完成以下编译期接入：

1. 创建 `app/<应用名>/` 及其子包。
2. 创建 `app/<应用名>/application.go`。
3. 在 HTTP 入口空导入 `thinkgo/app/<应用名>`。
4. 重新编译服务。

## 5. 应用运行时模型

`framework.App` 代表一个具体应用的运行时，不再代表所有应用。每个应用实例独立持有：

- 应用级容器和依赖绑定。
- 应用级配置、环境快照和调试状态。
- 应用级路由和中间件管道。
- 应用级事件分发器和 Provider 生命周期。
- 应用级数据库、缓存、日志、视图、语言、Cookie 和 Session。
- 应用目录、运行时目录和 URL 应用上下文。

新增 `ApplicationManager` 负责读取已经编译进程序的应用定义，校验应用名和目录，创建所有应用实例并管理其生命周期。新增的统一 HTTP 宿主负责持有每个应用的 HTTP 请求处理器。

应用实例在启动阶段全部初始化并冻结。任何应用的配置、注册、路由或资源初始化失败，统一 HTTP 宿主都不得开始监听。应用启动完成后，路由和注册表只读；请求处理不能改变应用实例的共享结构。

单应用调用方使用 `framework.BuildApp` 或显式的 `NewAppUninitialized` + `Initialize` 流程，并继续使用 `App.Run` 生命周期。多应用入口使用 `ApplicationManager` 启动全部应用，再把统一 HTTP 宿主作为宿主内核运行；关闭时按应用注册逆序释放资源。旧构造函数兼容别名不属于当前 API。

## 6. 配置加载与初始化顺序

单个应用的初始化顺序固定为：

```text
校验应用定义和应用目录
    ↓
加载根目录 .env
    ↓
加载根目录 config/*.json
    ↓
加载 app/<应用名>/config/*.json
    ↓
创建应用级基础组件
    ↓
执行 application.go 注册回调
    ↓
加载 app/<应用名>/lang/*.json
    ↓
注册应用中间件、事件和 Provider
    ↓
加载应用路由
    ↓
冻结路由
    ↓
启动 Provider
```

根目录配置作为全局基础配置，应用配置在对应命名空间中覆盖基础配置。数据库、缓存、日志、视图、Cookie 和 Session 的相对路径必须基于应用根目录或 `runtime/<应用名>/` 解析，不能继续写入共享的单一运行时目录。

## 7. 应用解析规则

多应用配置使用 ThinkPHP 风格的配置名称：

```json
{
    "default_app": "index",
    "app_map": {},
    "domain_bind": {},
    "deny_app_list": [],
    "app_express": false
}
```

请求解析顺序如下：

1. 优先检查显式域名绑定，顺序为精确域名、子域名和通配域名。
2. 未命中域名绑定时，读取 URL 首段作为应用候选。
3. 先应用 `app_map` 别名映射，再检查应用定义中是否存在同名应用。
4. 应用候选命中后检查 `deny_app_list`，被禁止的应用直接返回 404。
5. URL 没有应用首段时使用 `default_app`。
6. 应用首段不是已注册应用时，根据 `app_express` 决定回退默认应用或返回应用解析错误。

路径应用会移除 URL 首段后交给目标应用：

```text
/admin/users  ->  admin 应用接收 /users
```

域名绑定应用只切换应用，不移除路径：

```text
admin.example.com/users  ->  admin 应用接收 /users
```

应用名、路径、域名和映射目标全部在宿主启动阶段验证。应用选择不得接受路径穿越、反斜杠、编码斜杠或控制字符。未知应用、禁止应用和非法应用路径不应泄露服务器文件系统信息。

## 8. 统一 HTTP 宿主与请求流程

统一 HTTP 宿主只启动一个 HTTP/TLS/HTTP3 服务。它持有应用名到应用 HTTP 处理器的只读映射：

```text
HTTP 请求
    ↓
MultiHttp 校验请求和 Host
    ↓
解析目标应用
    ↓
复制 http.Request 并重写路径
    ↓
目标应用 Http
    ├── 静态资源
    ├── 应用全局中间件
    ├── 应用路由
    ├── 控制器级中间件
    ├── 控制器动作
    └── 应用异常处理
    ↓
响应发送、终结中间件、HttpEnd 和访问日志
```

应用解析期间只能修改请求副本中的 `Path`、`RawPath` 和 `RequestURI`，必须保留查询参数、Host、TLS 和请求头。原始请求对象和其他应用实例不得被修改。

目标应用的 HTTP 处理器不再单独调用 `ListenAndServe`。网络监听、TLS 证书、HTTP/3 和宿主级超时由根配置统一管理；目标应用仍可以拥有自己的请求限制、可信代理、语言、Session、路由和业务中间件配置。

应用上下文需要随请求传递，包括应用名、应用目录、是否通过域名绑定、URL 路径前缀和原始请求路径。应用 URL 生成必须是请求安全的：

- 路径应用生成的 URL 自动包含应用前缀。
- 域名绑定应用生成的 URL 使用当前应用绑定域名。
- 默认应用继续生成不带应用前缀的 URL。
- 不通过修改共享 `App` 字段保存当前请求的应用前缀。

## 9. 生命周期与错误处理

多应用宿主生命周期如下：

```text
创建 ApplicationManager
    ↓
校验并创建全部 App
    ↓
初始化全部 App
    ↓
启动全部 Provider
    ↓
创建并启动 MultiHttp
    ↓
处理请求
    ↓
停止 HTTP 宿主
    ↓
按逆序关闭全部 App
```

应用初始化错误必须在 HTTP 监听前返回。应用启动失败不允许只跳过失败应用后继续提供服务，避免生产环境出现部分应用可用、部分应用静默失效的状态。

请求阶段的错误只属于被选中的应用：

- 应用映射、禁止应用、非法路径以及 `app_express=false` 时无法命中的应用返回 404；`app_express=true` 时按配置回退到默认应用。
- 请求解析失败返回 400。
- 路由不存在由目标应用返回 404。
- 中间件、控制器 panic 由目标应用异常处理器转换响应。
- 一个应用关闭失败时，仍继续关闭其他应用，并聚合所有关闭错误。

每个应用分别触发自己的 `AppInit`、`RouteLoaded`、`HttpRun` 和 `HttpEnd` 生命周期事件。应用关闭时，Provider、缓存、数据库、日志和 Session 回收器仍遵循现有的安全关闭顺序。

## 10. 命令行和文档迁移

HTTP 入口改为导入应用入口包并创建多应用宿主。命令行行为调整如下：

- `run` 启动 `ApplicationManager` 和 `MultiHttp`。
- `make:controller`、`make:model`、`make:middleware`、`make:validate`、`make:event`、`make:service` 增加应用选择参数，默认读取 `default_app`。
- `route:list` 和 `config:dump` 支持指定应用，未指定时使用默认应用。
- `clear` 按应用清理 `runtime/<应用名>/`，不再假设只有一个运行时目录。

实施阶段迁移要求（已完成）：业务文件迁移到 `app/index/`，旧目录和旧入口导入已移除；架构章节中的单应用描述、多应用“不支持”描述、根目录路由路径和入口示例已同步更新。

## 11. 测试和验收标准

实施遵循测试驱动开发，先补充失败测试，再实现对应功能。测试至少覆盖：

### 11.1 应用定义和注册

- 应用名、应用路径和应用定义重复校验。
- 同名控制器在不同应用之间可以独立注册。
- 同名路由和中间件在不同应用之间互不覆盖。
- 应用注册回调错误和 panic 都能转为启动错误。

### 11.2 应用解析

- 默认应用。
- URL 首段应用。
- `app_map` 别名。
- 精确域名、子域名和通配域名绑定。
- `deny_app_list`。
- `app_express` 回退。
- 应用路径重写、查询参数保留和编码路径安全。
- 非法应用名、路径穿越、反斜杠和编码斜杠拒绝。

### 11.3 隔离和并发

- 不同应用的容器绑定、配置、路由、事件、语言包、日志、缓存、数据库和 Session 目录互不影响。
- 两个应用同时处理请求时不会共享请求状态或控制器实例。
- 应用 URL 前缀在并发请求中不会串扰。
- Provider 启动和关闭顺序在多个应用之间稳定。

### 11.4 HTTP 集成

- 一个监听器可以向不同应用分发请求。
- 应用路由和控制器返回结果正确。
- 目标应用的中间件、异常处理和访问日志生效。
- 一个应用初始化失败时 HTTP 宿主不监听。
- 关闭错误会继续释放其他应用并返回聚合错误。

### 11.5 迁移和回归

- 现有框架测试、控制器分发测试、路由测试和命令行测试全部更新到 `app/index` 结构。
- `go test ./...` 通过。
- 对应用生命周期、应用解析和 HTTP 宿主执行 `go test -race`。
- 通过有业务意义的测试覆盖注册、解析、隔离、异常和关闭路径，不使用仅为提高覆盖率的空测试。

## 12. 实施完成判定

只有同时满足以下条件，才认为多应用升级完成：

1. 项目源码只使用 `app/<应用名>/` 作为应用业务边界。
2. 同一进程可以通过 URL 和域名将请求分发到不同独立应用。
3. 应用之间的注册表、容器、配置、路由和运行时资源互不污染。
4. 应用初始化、Provider 生命周期、请求异常和关闭错误均有稳定错误语义。
5. 命令行生成路径、运行服务和文档引用均已同步。
6. 测试、竞态检查和完整回归验证通过。
